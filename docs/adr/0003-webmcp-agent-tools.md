# ADR-0003: 공개 페이지의 WebMCP 도구 노출

## Status

Proposed

## Context

브라우저 내장 에이전트가 사이트를 다루는 방식이 픽셀·DOM 추론에서 구조화된 도구 호출로 옮겨가고 있다.
Chrome은 이를 WebMCP로 표준화 제안 중이며 오리진 트라이얼(Chrome 149+)로 두 경로를 제공한다 —
명령형 `document.modelContext`(Chrome 150+. 구 `navigator.modelContext`는 폐기)와 `<form>`에 속성을
붙이는 선언형 API다. 도구는 탭에 바인딩되는 일시적 표면이라 상시 서버가 필요 없다.

이 저장소에는 이미 에이전트 표면이 둘 있지만 외부 에이전트는 어느 쪽도 쓸 수 없다.
인-앱 챗봇은 서버 키로 도는 Route Handler(ADR-0001)이고, 통합 Search는 브라우저 안에서만 도는
키워드 검색이다. 외부 에이전트에게 이 사이트는 여전히 해석해야 할 DOM 덩어리다.

사이트는 방문자에게 읽기 전용이고 쓰기는 관리자 1명뿐이다(CLAUDE.md 원칙 #7). 노출 가능한 표면이
공개 콘텐츠로 이미 한정돼 있어, 도구화의 위험은 "무엇을 쓰게 하느냐"가 아니라 "무엇을 읽혀
에이전트 판단을 오염시키느냐"에 있다. 문서가 지목하는 주된 위협도 간접 프롬프트 인젝션이다.

스펙은 확정 전이고, 이미 API 진입점이 한 번 옮겨간 전례가 있다.

## Decision

- **공개 트리에만 등록하고 쓰기 도구는 만들지 않는다.** `/admin/*`에는 도구를 마운트하지 않으며,
  등록 훅이 경로를 한 번 더 확인해 관리자 트리에서는 no-op으로 끝낸다. 도구를 통한 Firestore·Storage
  쓰기 경로는 존재하지 않는다.
- **`document.modelContext` 접근은 `lib/webmcp/model-context.ts` 어댑터 한 파일에 가둔다.**
  기능이 없는 브라우저에서는 전 구간 no-op이다 — WebMCP는 순수 프로그레시브 인핸스먼트이며
  어떤 기능도 이 API의 존재를 전제하지 않는다.
- **도구는 전역과 페이지 스코프 2계층으로 둔다.** 전역은 공개 레이아웃이 등록하는 `search_portfolio`·
  `get_profile` 둘뿐이고, 나머지는 해당 client component가 마운트된 동안만 산다. 등록 해제는
  `AbortController`를 effect cleanup에 걸어 페이지를 떠나면 자동으로 사라지게 한다.
  한 페이지에서 에이전트에게 보이는 도구는 5개 이하로 유지한다(전역 2 + 페이지 스코프 최대 3).
- **도구는 새 데이터 소스를 만들지 않는다.** 페이지 스코프 도구는 서버 컴포넌트가 이미 내려준 props를
  쓰고, 전역 검색은 `/api/search-index`(ISR 1시간)를 쓴다. Firestore 읽기 증가는 0이며 도구는
  `/api/chat`을 호출하지 않는다 — 외부 에이전트가 이 사이트의 LLM 비용을 발생시킬 경로를 두지 않는다.
- **도구 이름·설명·스키마는 영어로 고정한다**(에이전트가 읽는 코드). 출력 텍스트는 현재 URL 로케일을
  `pickText`로 따르고, 반환 경로에는 `localizePath`로 같은 로케일 프리픽스를 붙인다 — 프리픽스 없는
  경로는 308(`/ko/*` 직행)이나 루트 307 판정을 타므로, 도구를 따라간 에이전트가 방문자의 언어를
  바꿔놓을 수 있다(ADR-0002).
- **교차 출처는 열지 않는다.** `exposedTo`를 지정하지 않아 동일 출처로 두고, `Permissions-Policy`에
  `tools=(self)`를 명시해 기본값 의존 대신 문서화된 거부로 만든다.
- **annotation은 실제 효과대로 붙인다.** 데이터를 바꾸지 않는 조회 도구는 `readOnlyHint: true`,
  UI 상태(필터·모달)를 바꾸는 도구는 `false`. 공개 콘텐츠 작성자가 관리자 1명뿐이라
  `untrustedContentHint`는 현재 `false`지만, 방문자 생성 콘텐츠가 생기는 순간 해당 도구는 `true`로 뒤집는다.
- **문자 예산을 설계 제약으로 받는다** — 도구 설명 500자, 파라미터 설명 150자, 이름 30자, 출력 1,500자.
  목록 도구는 기본 8건에 제목·메타·경로만 담고, 상세 도구는 원문 전체가 아니라 요약을 반환한다.
- **연락 폼은 선언형 API만 붙이고 `toolautosubmit`은 쓰지 않는다.** hCaptcha 토큰은 사람만 만들 수
  있어 자동 제출은 구조적으로 실패하며, 발송은 사람의 확인을 거친다. 에이전트의 역할은 입력 채우기까지다.
- **오리진 트라이얼 토큰은 `NEXT_PUBLIC_WEBMCP_ORIGIN_TRIAL_TOKEN`으로 주입**하고 미설정 시 meta를
  넣지 않는다. 별도 기능 플래그는 두지 않는다 — 토큰을 지우면 트라이얼이 꺼지고 API가 사라지므로
  환경변수 하나가 그대로 킬 스위치다.

## Consequences

- 외부 에이전트가 검색·필터·상세 열람을 함수 호출로 수행한다. 같은 동작을 DOM 추론으로 재현하던
  실패(잘못된 칩 클릭, 모달 미인식)가 사라진다.
- 챗봇과 WebMCP는 대칭 표면이 된다 — 챗봇은 사이트가 호스팅하는 에이전트, WebMCP는 방문자가
  데려온 에이전트다. 둘은 `SearchDocument` 투영을 공유하지만 런타임은 완전히 분리된다.
- 검색 랭킹·사진 필터 로직을 UI와 도구가 같은 `_lib` 함수로 공유하므로, 한쪽만 바뀌어 결과가
  갈라지는 드리프트가 구조적으로 막힌다. 대신 그 함수들의 시그니처가 사실상 공개 계약이 된다.
- 오리진 트라이얼이 끝나거나 API가 다시 이름을 바꾸면 어댑터 한 파일과 훅의 타입만 고친다.
  기능 감지가 실패 경로이므로 스펙이 깨져도 사이트는 조용히 예전처럼 동작한다.
- 운영 비용·CSP는 그대로다. 새 외부 호스트가 없어 `security-headers.ts`의 변경은 `tools=(self)`
  한 줄뿐이고, Firestore 읽기와 Vercel 함수 호출은 늘지 않는다.
- 확률적 소비자가 생기므로 테스트 축이 하나 늘어난다. 도구 실행은 결정론적으로 단위 테스트하되,
  도구 선택·순서·인자는 Tool Inspector 기반 수동 평가로만 확인하고 CI에 넣지 않는다.
- 지원 브라우저가 아직 좁아 당분간 실사용자 대부분에게는 아무 효과가 없다. 이 작업은 회귀 위험이
  낮은 선행 투자이며, 그만큼 기존 UI 코드를 도구를 위해 재구성하지 않는다.
