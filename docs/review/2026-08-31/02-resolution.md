## 리뷰와 달랐던 것

**C2 는 자르기 한 줄로 닫히지 않았다.** 보고서는 "자르는 지점이 셋" 까지 적었는데, 넷째가
있었다. `renderCards` 가 `input !== null` 인 entry 전부를 분석 대상으로 모으고
`buildPerformanceTriageCards` 가 `entries.length !== targets.length` 로 개수를 대조한다.
보내는 개수만 20 으로 줄이면 이 대조가 26 대 20 으로 어긋나 분석이 **전부** 버려진다.
결함의 증상이 그대로 남는다. 카드 쪽 분할까지 같은 선택을 알아야 닫히는 문제였다.

**그래서 `selected: boolean` 으로는 부족했다.** 심각도 정렬이 순서를 바꾸는데
`PerformanceTriageTarget.targetIndex` 는 요청 배열의 위치를 가리킨다. 원래 entry 순서로
다시 모으면 분석이 다른 카드에 붙는다. 불리언 대신 `triageOrder` 로 순위를 값으로 실어
요청 순서, 응답 인덱스, 카드 순서를 한 값에 묶었다. 검토 단계에서 이 지적을 받아 계획을
바꿨다.

**C6 과 C12 는 같은 결함의 두 얼굴이 아니라 셋이었다.** 보고서는 집계(C6)와 표시(C12)를
적었는데, 대표 실행 선택에도 같은 편향이 있었다(C14). 셋 다 "이 metric 은 클수록 좋은가" 를
아무도 모르는 데서 나왔다. 세 자리를 각각 고치면 네 번째가 또 나올 자리라
`metric-descriptor` 를 만들어 방향과 단위와 척도를 한 벌로 뒀다.

**척도는 판정 임계값이 될 수 없었다.** 처음에는 `goodThreshold` 라는 이름으로 판정 값을
그대로 쓰려 했다. 그런데 field LCP 경계는 2,500ms 인데 lab 경계는 3,000ms 이고 점수 경계는
0.8 이다. 하나를 고르면 다른 쪽이 틀리고, 둘 다 담으면 `source` 인자가 필요해진다.
비교 척도와 판정을 분리하고 이름을 `severityScale` 로 바꿨다. 판정은 `performance-status`
가 계속 단독으로 소유한다.

**정렬용 값과 표시용 값도 갈랐다.** 방향을 보정한 악화량 하나로 둘을 겸하면 점수 하락
0.10 이 카드에 `+0.10` 으로 찍힌다. 실제 변화는 `-0.10` 이다. `severityRatio` 는 항상 양수
악화 크기를 내고 `formatDelta` 는 실제 부호를 따른다.

**C10 은 shard 개수를 옮기는 문제가 아니었다.** 워크플로 `matrix` 는 env 를 읽지 못해
리터럴 하나는 어떻게 해도 남는다. 개수를 맞춰도 한 shard 가 통째로 비면 통과한다.
세는 대상을 바꿔 병합 결과가 지켜야 할 계약을 봤다. 대상 집합 일치, 대상별 실행 2~3개,
대표 실행 정확히 하나. 검토 단계에서 "URL 존재만 보면 실행 구성이 통과한다" 는 지적을 받아
뒤 둘을 넣었다.

## 리뷰가 놓친 것

**`cards` 와 `triageInputs` 의 인덱스 정렬이 이미 취약했다.** `report-decision.ts` 는
`cards` 를 `flatMap` 으로, `triageInputs` 를 `map` 으로 만든다. 카드가 하나라도 `null` 이면
길이가 갈려 스크립트의 위치 기반 짝짓기가 어긋난다. 지금은 `baseline` 만 `null` 을 낼 수
있고 그 report 는 `sendBaseline` 이 참일 때만 만들어져 도달하지 않는다. 잠복 상태로 남는다.

**`markRepresentativeRun` 의 편향은 값이 아니라 진단에 영향을 준다.** C6 과 묶어 고쳤지만
증상은 다르다. 집계값은 `aggregateValues` 가 정하고 진단 문구는 대표 실행 하나에서만
읽으므로, 고치기 전에는 두 함수가 서로 다른 실행을 가리켰다. 카드의 수치와 AI 가 읽는
원인 후보가 다른 측정에서 나오는 상태였다.

**`metrics.slice(0, 12)` 의 상한이 실제 행 수보다 작았다.** combined 대상은 url·origin 의
field 여섯 행에 lab 일곱 행을 더해 13행이다. 상한 12 는 이 계산 없이 정해진 값으로 보인다.
정렬을 넣어 버려지는 행을 통제했지만 상한 자체의 근거는 여전히 없다.

**테스트 stub 이 타입을 지키지 않고 있었다.** `core-web-vitals-report.test.ts` 의
`triageInputs` fixture 가 `{ target: "/ko" }` 뿐이라 `metrics` 가 없었다. 스크립트가
`unknown` 을 캐스팅해 넘기므로 컴파일은 통과했고, 선택 로직이 그 배열을 읽는 순간 처음
드러났다. 방어 코드를 넣는 대신 fixture 를 타입에 맞췄다. 실제 생산 경로는
`buildPerformanceDecision` 이 항상 `metrics` 를 채운다.

**`report-decision.ts` 의 두 수정은 한 hunk 를 공유했다.** C5 의 `registerAlert` 재배치와
C8 의 `insufficient` 타입 변경이 같은 열 줄 안에서 만난다. 커밋을 나누려면 중간 상태를
직접 만들어야 했다. 파일 단위로 커밋을 계획하면 이런 자리가 나온다.

## 남은 것

**02 문서에는 열린 항목이 없다.** 03 문서의 구조 후보 넷은 그대로다. 이번 라운드가
`metric-descriptor` 를 만들었지만 그것은 `performance-alerts` 안의 모듈이고, 세 계열이
공유하는 전송·예산 계층은 여전히 세 벌이다.

**`cards` 와 `triageInputs` 의 인덱스 정렬.** 위 "리뷰가 놓친 것" 의 첫 항목이다.
도달 불가라 이번 범위에 넣지 않았다. 카드를 만들지 않는 report 종류가 하나라도 늘면
그때 짝을 한 번에 만드는 구조로 바꿔야 한다.

**`metrics.slice(0, 12)` 의 상한.** 정렬로 증상은 막았지만 combined 대상은 여전히 한 행을
잃는다. 상한을 올릴지 결정하려면 프롬프트 길이와 비용을 함께 봐야 한다.

**수동 dispatch.** 아래는 단위 테스트로 닿지 않는다.

- 새 병합 계약으로 `Merge Lighthouse shards` 단계가 통과하는지
- 강제 실행 뒤 snapshot 의 `sentAlerts` 에 이번 경고 key 가 들어가고, 이어지는 정기 실행이
  같은 회귀로 카드를 다시 보내지 않는지 (C5)
- 통합 카드의 `가장 크게 악화` 줄과 `상세` 링크 (C12·C13)

뒤 둘은 조건부다. 경고가 하나뿐이면 통합 카드가 오지 않고, CLS 나 점수 경고가 없으면 표시
문제를 볼 수 없다. 실제 생성 카드는 항상 url 을 가지므로 C13 의 url 없음 경로는 재현되지
않는다. dispatch 는 배포 smoke test 이고 C12·C13 과 카드–분석 대응 계약의 주 검증은
단위 테스트다.
