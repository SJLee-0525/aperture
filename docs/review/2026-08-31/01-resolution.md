## 리뷰와 달랐던 것

**S1 은 버그가 아니라 계약이었다.** 보고서는 "pathname 을 남긴다" 를 누락처럼 적었는데,
`core-web-vitals-report.test.ts:189-196` 이 `https://example.com/path?api_key=secret` →
`https://example.com/path` 를 단언하고 있었다. 쿼리만 지우고 엔드포인트는 디버깅에 쓰겠다는
의도가 테스트로 고정돼 있었다. 고치는 일은 한 줄 수정이 아니라 계약 변경이고, 기존 기대값을
함께 뒤집어야 했다.

노출 조건도 보고서보다 좁았다. 세 번째 치환 규칙
`(api[_-]?key|token|webhook)(\s*[=:]\s*)[^\s]+` 가 `webhook=` 접두사가 붙은 URL 을 통째로
지운다. `core-web-vitals-report.test.ts:107-113` 이 그 경로를 이미 단언한다. 실제로 새는 것은
접두사 없이 맨 URL 만 들어오는 경우다. 그래도 고친 이유는 유출 가능성이 아니라, 같은 목적의
방어를 두 스크립트가 서로 다른 강도로 적용하고 있었기 때문이다.

**S2 는 심각도가 틀렸다.** 중간으로 적었으나 근거가 둘 다 약했다.
ADR-0006 이 sentry 에 상한을 요구한 이유는 Sentry 웹훅이 **외부 트리거**라 오류 폭주 시 한 번에
수백 번 호출될 수 있어서다. 신규 둘은 cron 자기 트리거이고, 남는 노출은 관리자 본인이
`workflow_dispatch` 를 반복 실행하는 경우뿐이다. 같은 계열이라고 해서 같은 방어가 필요한 것은
아니었다.

더 결정적인 것은 지금 붙여도 동작하지 않는다는 사실이다. 두 워크플로 어디에도
`UPSTASH_*` 와 `KV_REST_API_*` 가 없어 `triage-rate-limit.ts:78-83` 의 fail-open 분기를 타고
상한 없이 통과한다. 코드를 넣는 것이 아니라 시크릿을 등록하는 것이 선행이다. 낮음으로 내리고
구현하지 않았다.

**S3 은 다른 문서의 항목과 묶여 있었다.** `recommendedChecks` 를 허용 목록으로 거르면 배열이
빌 수 있고, 빈 배열이 `확인 순서` field 를 빈 문자열로 만들어 Discord 가 400 으로 거부한다.
그것이 02 문서의 C1 이다. S3 만 고쳤다면 이미 알고 있던 높음 결함의 발생 빈도를 올렸을 것이다.
문서를 영역별로 나눈 덕에 읽기는 쉬웠지만, 수정 순서는 그 분할이 알려주지 않았다.

**S4 는 리뷰가 권고한 방향이 틀렸다.** 보고서는 performance-alerts 의 `textArray` 를 기준으로
"두 파서의 엄밀도가 다르다" 고 적었다. 그대로 맞추면 전체 거부가 된다. 그런데 두 파서는 짝
맞추기 모델이 다르다. performance-alerts 는 `targetIndex` 순서쌍이라 하나가 깨지면 전체를
버려야 하지만(`triage-schema.ts:127-131` 주석이 그 이유를 적는다), dependency-security 결과는
`discord-report.ts:69` 가 `alertNumber` 로 찾는다. 부분 결과가 성립한다.

전체 거부로 맞췄다면 사소한 슬립 하나로 열 건의 분석을 전부 잃었을 것이다. C2 가 보여준 과도한
전체 거부의 대가를 반복하지 않도록 어긋난 항목만 버리게 했다.

**S5 는 50대 50 이 아니었다.** 보고서는 "두 워크플로에서 다르다" 로 적었는데, 저장소 전체를
세어 보니 `checkout@v7` 12회, `setup-node@v6` 9회이고 `@v4` 를 쓰는 것은 Core Web Vitals
워크플로 하나뿐이었다. 논쟁 대상이 아니라 뒤처진 파일 하나였다.

## 리뷰가 놓친 것

**`dependency-security-report.ts` 에는 테스트가 아예 없었다.** 보고서는 이 파일의 자체 치환이
"Discord 전송 실패 한 줄에만 걸려 있다" 까지만 적었다. 실제로는 `main().catch` 가
`error.message` 를 그대로 출력해 두 번째 구멍이 있었고, 파일 전체에 테스트 파일이 없었다.

**그 파일은 테스트할 수 없는 구조였다.** import 만 해도 `main()` 이 돌았다. 헬퍼로 바꾸는
것만으로는 두 호출부가 실제로 헬퍼를 지나는지 고정되지 않는다. `core-web-vitals-report.ts:346`
의 직접 실행 가드 패턴을 옮겨 오고 CLI 진입점을 `runCli` 로 분리한 뒤에야 배선을 단언할 수
있었다. 검토 단계에서 이 제약을 지적받아 계획에 넣었다.

**`http://` 는 URL 정규식에 걸리지도 않는다.** 파싱 실패 폴백을 테스트하려고 처음 쓴 입력이
매치조차 되지 않아 통과했다. `[^\s?#]+` 가 `//` 뒤에 최소 한 글자를 요구한다. 매치는 되면서
`new URL()` 이 던지는 입력을 따로 찾아야 했고 `https://[` 를 썼다.

**시크릿 스캔 훅이 테스트 픽스처를 막는다.** `ghp_` 형태의 가짜 토큰 리터럴을 테스트에 넣으면
`.claude/hooks/secret_scan.py` 가 쓰기를 거부한다. 훅을 우회하지 않고 문자열을 조립해서 만들고
그 이유를 테스트 파일 주석에 남겼다.

**제목을 바꾸면 앵커가 끊긴다.** 닫힌 항목을 "처리됨" 절로 옮기며 제목을 고치자 다른 문서에서
거는 링크 4개가 죽었다. 처음 쓴 `→ 닫힘` 표기는 GitHub 앵커에서 화살표가 제거되며 하이픈이
두 개가 되는지 한 개가 되는지 모호했다. 괄호 표기로 바꿔 없앴다. CLAUDE.md 가 장식용 화살표를
금하는 것과도 맞는다.

## 남은 것

**S2 구현.** 강등했지만 비용 자체가 없다는 뜻은 아니다.
`triage-prompt.ts:56` 의 `performanceTriageOutputTokens` 는 대상 수에 비례해 출력 예산을
16,000 토큰까지 올린다. 두 워크플로에 Upstash 시크릿을 등록하기로 하면 그때 상한을 붙인다.
등록 없이 리미터만 넣는 것은 무동작이므로 순서가 뒤바뀌면 안 된다.

**수동 dispatch.** 아래 셋은 단위 테스트로 닿지 않아 아직 확인되지 않았다.

- 상향한 `checkout@v7` / `setup-node@v6` 로 job 이 통과하는지
- Discord 에 카드가 실제로 도착하는지
- Actions summary 와 `core-web-vitals-ai-report` artifact 에 분석이 남는지

`force_ai_analysis=true` 로 돌려야 한다. 그러지 않으면 현재 경고가 없거나 중복 억제된 실행에서
AI 보고서가 생성되지 않는 것이 정상이라 셋째를 볼 수 없다. 이 옵션은 실제 provider 호출 비용과
실제 Discord 알림을 발생시킨다.

이것은 배포 smoke test 이지 C1 회귀 재현이 아니다. 실제 provider 가 두 배열을 모두 비워
응답한다는 보장이 없다. C1 회귀는 단위 테스트가 막는다.
`PERFORMANCE_TRIAGE_PROVIDER=mock` 로컬 실행도 대체가 되지 않는다.
`triage-provider.ts:27` 의 `mockResult` 가 `recommendedChecks` 에 항상 한 개를 넣어
빈 목록 경로를 지나가지 않는다.
