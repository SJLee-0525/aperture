# 검토 방법

## 범위를 이렇게 잡은 이유

Discord 로 카드를 보내는 경로가 셋이 됐다. Sentry 오류 트리아지가 먼저 있었고,
주간 의존성 보안 리포트와 Core Web Vitals 알림이 그 위에 얹혔다.
셋은 서로를 모르는 척하지만 같은 웹훅 전송 계층을 쓰고 같은 LLM 호출 규약을 따른다.

그래서 커밋 범위(`5d8b5c27` 이후)에 `sentry-triage` 전체를 더해 한 덩어리로 봤다.
신규 코드만 보면 "이 사본이 저 사본과 다르다"는 사실 자체가 보이지 않는다.

`src/` 의 나머지는 보지 않았다. 2026-08-26 검토가 이미 다뤘고, 범위를 넓히면 얕아진다.

## 적용한 기준

[2026-08-26 검토](../2026-08-26/08-method.md)의 역할 표에서 이 범위에 해당하는 것만 가져왔다.

| 역할           | 적용 기준                                 |
| -------------- | ----------------------------------------- |
| 서버 경계 보안 | `security-and-hardening`                  |
| 인증·인가      | `auth-implementation-patterns`            |
| 서버 정확성    | `code-review`                             |
| 구조           | `improve-codebase-architecture`           |
| 도메인 대조    | `web-perf` (Core Web Vitals 임계값)       |
| 규약           | CLAUDE.md, CONTEXT.md, ADR-0006 직접 대조 |

UI 계열 기준(`frontend-ui-engineering`, `fixing-motion-performance`,
`react-state-management`)은 제외했다. 이 범위에 렌더되는 화면이 없다.

`web-perf` 는 원래 브라우저를 띄워 페이지를 측정하는 도구다.
여기서는 그 문서가 들고 있는 Core Web Vitals 경계값을 `performance-status.ts` 의
상수와 대조하는 데 썼다. 코드가 인코딩한 도메인 지식을 외부 기준으로 확인한 셈이다.

## 두 번 읽었다

1차는 보안과 구조 렌즈로 직접 전수 읽기. 38개 비테스트 파일과 스크립트 5개,
워크플로 2개를 샘플링 없이 열었다.

2차는 `code-review` 를 정확성 렌즈로 별도 실행. 같은 코드를 다른 목적으로 다시 읽게 했다.

두 패스가 겹치지 않았다. 1차만 찾은 것이 빈 field 로 인한 Discord 400 과
performanceScore 집계 방향이고, 2차만 찾은 것이 강제 재분석의 두 결함과
통합 카드가 측정값을 버리는 문제다.
겹친 항목은 하나인데, 그 하나에서 2차가 1차의 심각도 판정을 뒤집었다.

## 심각도를 뒤집은 사례

`MAX_TARGETS` 경계 어긋남을 1차에서는 낮음으로 적었다. "대상 21개 이상은 드물다"는
이유였는데, 도달 경로를 잘못 봤다.

`report-decision.ts:134` 가 Lighthouse 의 `mobile` 을 `phone` 키로 합치므로
그룹 수는 최대 26개다. 그리고 `force_ai_analysis` 는 중복 억제를 건너뛰어
현재 경고 전부를 한 번에 리포트로 만든다. 20을 넘는 것이 강제 실행의 정상 동작이다.

높음으로 올렸다. 빈도 추정을 코드로 확인하지 않은 것이 원인이다.

## 주장을 무너뜨리려 했다

세운 가설을 그대로 적지 않고 "이게 틀렸다면 왜 틀렸을까"를 먼저 물었다.
다섯 건이 무너졌고 전부 [07-rejected.md](07-rejected.md) 에 남겼다.

무너뜨린 방법은 셋이다. 문서의 범위를 다시 읽기(환경변수), 실행 이력 확인하기
(`gh run list`), 도구에게 직접 묻기(ESLint `--format json`).
기억으로 API 계약이나 린터 동작을 단정한 것이 실패 원인이었다.

## 재검토 (`84509d7`)

보고서를 쓰는 동안 통합 카드 재설계와 강제 재분석 수정(`84509d7`)이 들어왔다.
전 항목의 줄번호와 성립 여부를 그 커밋 기준으로 다시 대조했다.

- C3·C4·C7 이 닫혔다. 카드 재설계가 집계 현황과 상세 링크를 복원했고,
  lab 경고가 강제 재분석에 포함됐으며, 새 카드는 6,000자 상한에 도달하지 않는다.
- C5 는 넓어졌다. C4 수정이 같은 단락 평가 패턴을 lab 경로에 복제해,
  강제 실행에서 key 를 기록하지 않는 경로가 둘에서 셋이 됐다.
- 새 집계 코드에서 두 건이 나왔다. C12(performanceScore 방향과 CLS 반올림)와
  C13(가드 없는 url 보간)이다.
- 범위 내 테스트는 370개로 늘었고 전부 통과한다(1.35초).

수정 커밋이 리뷰 항목을 닫으면서 같은 부류의 결함을 새로 만드는 것까지가
복제 구조의 비용이다. [03](03-architecture.md) 후보 1·2 가 그 구조를 다룬다.

## 이 보고서를 읽는 법

- 심각도는 재검증 후 값이다. 1차 판정과 다를 수 있고, 뒤집힌 것은 위에 적었다.
- 줄번호는 재검토 기준 `84509d7` 값이다.
- 구조 항목([03](03-architecture.md))은 결함이 아니라 제안이다. 후보 1은
  ADR-0006 의 결정을 다시 여는 것이므로 착수 전에 합의가 필요하다.
- [07-rejected.md](07-rejected.md) 를 먼저 훑으면 이미 무너진 주장을 다시 조사하지 않는다.

## 한계

- Discord 에 실제로 카드를 보내 400 을 재현하지 않았다. 높음 1건은 API 계약과
  코드 경로 추적으로 세웠다.
- LLM 제공자의 실제 응답을 받아보지 않았다. 모델이 빈 배열을 돌려주는 빈도는 모른다.
- 워크플로를 실제로 실행해 shard 분할이나 artifact 왕복을 관찰하지 않았다.
  성공 이력만 확인했다.
- 두 파이프라인의 비용을 실측하지 않았다. 상한이 없다는 사실만 코드로 확인했다.
