### 한 요소에 얹힌 두 클래스가 같은 속성을 다툰다 (두 번 물렸다)

먼저 글 상세에서 깨진 이미지 자리표시자가 히어로 이미지를 통째로 덮었다. 목록에서 글로
들어가 새로고침한 뒤 뒤로가기로 나갔다가 다시 들어가면 재현됐다.

`ImageFallback.module.css` 의 `.fallback` 과 `ArticleBody.module.css` 의 `.brokenFigure` 가 같은
요소에 얹히면서 둘 다 `position` 을 선언했다. 클래스 하나짜리 셀렉터라 명시도가 같아 승자를
**스타일시트 삽입 순서**가 정한다. 그 경로에서 순서가 뒤집히면 `position: absolute` 가 이기고,
글 본문에는 위치 지정 조상이 없어 자리표시자가 초기 컨테이닝 블록 기준으로 펼쳐진다.

그때 같은 부류를 전수로 찾았다고 적었다. **그 전수가 좁았다.** CSS 모듈 두 벌이 겹치는
경우만 봤다. 며칠 뒤 지도가 사라졌고, 원인은 모듈과 **라이브러리가 런타임에 붙이는 클래스**의
같은 다툼이었다. 지도 컨테이너는 우리 `.canvas`(`position: absolute; inset: 0`)와 maplibre 가
직접 다는 `.maplibregl-map`(`position: relative`)을 함께 단다. relative 가 이기면 `inset` 이
무시돼 요소 높이가 0 이 되고, maplibre 는 높이 0 을 `clientHeight || 300` 으로 받아 캔버스를
300px 에 고정한다. 너비는 제 값이고 높이만 300px 인 상태가 그 결과다. 사진 상세의 미니맵도
같은 구조였다.

두 번째로 물린 뒤에는 범위를 넓혀 다시 훑었다. 새로 나온 것 셋을 더 고쳤다.

| 자리                                                  | 다툰 속성                | 결과                                                                     |
| ----------------------------------------------------- | ------------------------ | ------------------------------------------------------------------------ |
| `MiniMapCanvas` ↔ `.maplibregl-map`                   | `position`               | 지도와 같은 방식으로 300px 에 고정된다                                   |
| `ArticleForm .inlineField` ↔ `AdminField .field`      | `min-width` (120px vs 0) | **값이 다르다.** 순서가 뒤집히면 관리자 인라인 필드가 하한 없이 무너진다 |
| `TagAddForm .fieldText`, `SearchSuggestions .section` | `min-width`, `color`     | 값이 같아 무증상. 순서에 기대는 것은 같다                                |

`AdminField` 는 폭 하한을 `--admin-field-min-width` 변수로 열었다. 호출부가 자기 클래스에
같은 속성을 적는 대신 값만 넘기므로 다툴 속성 자체가 없어진다.

그리고 검사를 저장소에 남겼다(`scripts/find-css-class-clashes.mjs`). 세 경로를 본다 — 한 JSX
요소에 직접 얹힌 클래스들, `className` 을 prop 으로 받아 합치는 컴포넌트와 그 호출부,
maplibre 가 클래스를 다는 요소다. maplibre 쪽 속성은 실제 `maplibre-gl.css` 를 읽어 뽑는다.
같은 스타일시트 안의 base+modifier 는 대상이 아니다. 그쪽은 작성 순서가 승자를 정한다.
지도 결함을 되돌리면 그 줄을 짚어 실패하는 것까지 확인했다.

규칙은 [public-ui-conventions.md](../../public-ui-conventions.md) 에 적었다.

### 갤러리 사진 모달의 연출

작업 그리드에서 연 모달은 닫힘 연출이 없었고 열림도 앨범과 달랐다. 원인이 넷이었다.

- **닫힘**: `AnimatePresence` 가 `PhotoModal` 안에 있는데 온디맨드 경로가 컴포넌트를 통째로
  언마운트했다. 퇴장이 돌 대상이 사라진다. 상세를 한 번이라도 받으면 계속 마운트해 둔다.
- **두 번째 열기**: `readyId` 초기화가 `close()` 안에만 있어 뒤로가기로 닫으면 남았다. 다 본
  사진의 id 가 남으면 같은 사진을 다시 열 때 판정이 이전 열기를 물려받는다.
- **열림**: 등장이 두 번으로 나뉘어 있었다. 로딩 프레임이 스크림을 올리고, 사진이 도착한 뒤
  패널이 따로 들어왔다. 검정 레이어가 먼저 오르고 모달이 뒤따르는 것처럼 보인 이유다.
- **오버레이 stack**: 퇴장 연출을 위해 모달을 닫힌 뒤에도 마운트해 두면서, 마운트 여부로
  판정하던 `useOverlayLayer` 가 stack 을 영구 점유했다. 사진을 한 번 연 뒤에는 다른 오버레이가
  Escape 를 받지 못한다. C22 가 만든 회귀다.

로딩 프레임을 180ms 늦춰서 해결했다. 그 안에 열리면 프레임이 뜨지 않고 모달이 스크림과 패널을
함께 띄운다. 이웃 사진은 미리 받아 두므로 대부분이 이 경로다. 늦게 오는 경우에만 스크림과
스피너가 뜨고, 사진이 도착하면 스피너만 걷히며 패널이 그 자리에서 등장한다. 로딩 프레임에
Escape 도 붙였다. 사진이 늦게 오는 동안 닫을 방법이 닫기 버튼뿐이었다.

### 지도가 사라진다

지도에서 사진을 열고 닫으면 타일과 핀이 함께 사라졌다. 위의 `position` 다툼이 절반이고,
나머지 절반은 C21 이 만든 회귀다.

C21 은 상세를 여는 URL 쓰기 경로를 하나로 모으면서 지도 핀 클릭도 `openDetailQuery`(raw
`history.pushState` + 합성 `popstate`)로 바꿨다. App Router 는 자기가 만들지 않은 entry 에
popstate 를 받으면 그 세그먼트를 다시 마운트한다. 그때 maplibre 인스턴스가 통째로 죽는다.

계측으로 갈랐다. 목록 링크(진짜 내비게이션)로 열면 재마운트가 없고, 핀으로 열면
`MAPCANVAS_INIT → TEARDOWN → INIT` 이 찍힌다. 지도만 라우터로 되돌렸다. `detailQueryHref` 를
그대로 쓰므로 C21 이 고치려던 성질(기존 query 를 버리지 않는다)은 유지된다. 왜 지도만 다른
방식인지는 그 자리에 적었다.

`MapCanvas` 도 마운트당 한 번만 지도를 만들도록 고쳤다. 콜백이나 배열의 참조가 바뀌었다고
다시 만들면 같은 컨테이너에 인스턴스가 둘 생기고, 먼저 것이 제거될 때 캔버스만 남는다.
위치 목록이 바뀌면 소스 데이터만 갈아 끼운다. 방문자가 옮겨 둔 화면 위치와 줌도 함께 남는다.

## 적용한 구조 패턴

이번 작업이 반복해서 쓴 형태와 그 자리에서 산 것이다. 이름은 통용되는 것을 썼고, 단순한
함수 추출까지 패턴으로 부르지는 않았다.

### 팩토리 함수와 클로저 상태

`createCursorState` · `createAutoScrollController` · `createCursorLoadingRegistry` ·
`createChatRequestDeadline`.

`CustomCursor` 는 570줄짜리 effect 하나에 가변 지역 변수 스물넷을 들고 있었다. 상태가 클로저
안에 갇혀 인터페이스로 볼 수도 테스트할 수도 없었다. 상태를 클로저에 두되 setter 만 밖으로
내면 이름 있는 인터페이스가 생긴다. 그 덕에 모드 판정 사다리(자동 스크롤 > 휠 > 지도 > 호버 >
대상 > 점)를 jsdom 에서 잰다.

### 합성 훅

`useDialog` 가 포커스 트랩·스크롤 잠금·Escape·격리·최상위 판정의 조립을 갖는다.

이 다섯은 함께 켜지고 함께 꺼지는데 오버레이 여섯이 그 조합을 손으로 적으면서 조금씩 다른
집합을 골랐다. 규칙이 모듈이 아니라 여섯 벌의 호출 순서에만 있었다. 실제로 다른 부분만
인자로 받는다 — 오버레이마다 모바일 스크롤 처리가 다르다.

`PhotoModal` 은 옮기지 않았다. 셋의 활성 조건이 서로 다르다. 트랩은 진입 애니메이션이 끝난
뒤, 스크롤 잠금은 열리는 즉시, 최상위 판정은 사진이 있는 동안이다. 하나로 묶으면 셋 중 둘의
시점이 바뀐다.

### 오케스트레이터와 단계

`handle-chat-request` 를 본문 파싱 · 사용량 판정 · 마감 · 답변 생성 넷으로 나눴다.

730줄 함수 하나가 일곱 단계를 순차로 하고 주입 파라미터가 열하나였다. 한 단계를 검증하려면
매번 전체 파이프라인을 세워야 해서 소스 730줄에 테스트가 1,267줄이었다. 이제 각 단계가 자기
모듈에 있고 오케스트레이터는 순서와 실패 처리만 갖는다.

### 셸 컴포넌트

`AdminFormShell` · `AdminListShell` · `AdminSortableListPage` · `.u-page-main` 유틸리티.

같은 골격을 여러 화면이 각자 적고 있을 때, 골격을 한 번 쓰고 다른 부분만 넘긴다. 관리자 폼
여섯이 26줄짜리 골격을 각자 적었고, 공개 지면 열두 곳이 폭·가운데 정렬·상하 여백 네 줄을
각자 적었다.

### 단일 출처에서 파생

`--page-max` 토큰 하나를 열일곱 파일이 참조한다. `PHOTO_GRID_BREAKPOINTS` 하나에서
`matchMedia` 질의와 `next/image` 의 `sizes` 문자열이 나온다. `ANALYTICS_QUERY_ALLOWLIST` 는
`DETAIL_QUERY_KEYS` 에서 파생한다.

따로 적으면 한쪽이 조용히 뒤처진다. CSS 는 상수를 읽을 수 없어 미디어 쿼리에 숫자가 남는데,
그 사실은 양쪽 파일에 적었다.

### 사용자 정의 속성으로 뒤집은 제어

`AdminField` 가 `min-width: var(--admin-field-min-width, 0)` 을 읽고 호출부는 값만 넘긴다.

프리미티브가 기본값을 선언하고 호출부가 같은 속성으로 덮으면, 두 클래스가 한 요소에서
다투게 되고 승자를 스타일시트 삽입 순서가 정한다. 프리미티브가 변수를 읽으면 그 속성을
선언하는 규칙이 하나뿐이라 다툼 자체가 없다.

### 자기 입력을 들고 다니는 값

`assertWithinDocumentLimit` 이 `staleIds` 대신 그것을 만든 청크 id 를 함께 담은 교체 계획을
돌려주고, `replaceRagDocuments` 는 지금 저장하려는 청크와 다르면 던진다.

`string[]` 만 넘기면 다른 청크로 계산한 목록이 들어와도 타입이 막지 못한다. 그때 상한 검사가
조용히 건너뛰어지고 삭제 대상도 틀린다. 값이 자기 출처를 들고 다니면 그 상태가 오류가 된다.

### 계약을 이름으로

`pointer-chrome-contract` 가 커서와 스크롤바가 주고받는 DOM 표시 여섯을 갖는다.

두 컴포넌트는 서로를 import 하지 않고 DOM 속성으로만 만난다. 이름을 각자 하드코딩하면 어느
쪽을 바꿔도 ESLint 도 dependency-cruiser 도 끊어진 것을 보지 못한다.

### 관찰을 인자로

`useDetailQuerySession` 의 `openedOutside`.

사진은 타일과 지도 핀이 훅 밖에서도 상세를 열고 그 경로도 history entry 를 쌓는다. 나머지 셋은
훅이 유일한 쓰기 경로다. 이 차이를 "URL 이 null 에서 값으로 바뀌었더라" 는 관찰로 알아내던
것을 인자로 적었다.

시각 스냅샷은 한 번 갱신했다. `a3a6542` 의 캐스케이드 수정으로 자리표시자가 흐름 안에
자리를 차지하면서 글 상세가 길어졌고, 기준 이미지는 다툼에서 `absolute` 가 이긴 화면이었다.

지도 문제는 계측 없이는 못 잡았을 것이다. 처음 세운 가설 셋(컨테이너 크기, `map.resize()`
누락, ResizeObserver)이 전부 빗나갔고, 사용자가 보내 준 DOM 의 `width: 998px; height: 300px`
가 방향을 정했다. 너비는 제 값인데 높이만 상수라는 것이 `clientHeight || 300` 폴백을 가리켰다.
