## 3. 🔴 위험 — 먼저 고쳐야 할 3가지

### 3-1. 블로그 이미지 자동 정리가 살아 있는 사진을 지울 수 있다

**어디에**: `src/features/admin-maintenance/_lib/find-orphan-article-images.ts:79`

**어떻게 동작하나**

"안 쓰는 이미지 정리" 기능은 두 개의 목록을 비교합니다.

```
A. 글들이 쓰고 있는 이미지 목록   ← 글 DB에서 읽어 옴
B. 저장소에 실제로 있는 파일 목록  ← Storage에서 읽어 옴

B에는 있는데 A에는 없다  →  안 쓰는 파일이니 삭제
```

**무엇이 문제인가**

A가 잘못 나왔을 때 알아챌 방법이 없습니다.

글 조회(`listDevArticleImageRefsAdmin` → `listProjected`)는 오류가 나면 예외를 던지므로, "오류 없이 목록이 모자라게 오는" 경우는 사실상 하나입니다. 아래 3-2의 1000행 절단입니다. 글이 1000편을 넘으면 1001번째 이후 글이 쓰던 멀쩡한 이미지가 전부 삭제 후보가 됩니다. 즉 이 항목은 3-2가 고쳐지기 전까지 시한폭탄으로 남고, 3-2를 고친 뒤에도 "목록이 비정상적으로 작게 온 것을 감지하는 안전장치"는 별도로 필요합니다.

삭제 직전에 한 번 더 검사하긴 하는데, 똑같은 함수를 다시 부르는 방식이라 같은 오류가 그대로 반복됩니다. 안전장치 역할을 못 합니다.

더 걸리는 점은, 같은 저장소의 `article-body-storage-paths.ts` 주석에 이미 이렇게 적혀 있다는 것입니다.

> "한쪽이라도 놓치면 참조 집합이 비어 본문 이미지 전체가 미사용 삭제 후보가 된다."

위험을 알고 적어 뒀는데 코드에는 방어가 없습니다.

**어떻게 고치나**

```ts
// 삭제 대상이 전체의 절반을 넘으면(글 0건 포함) 자동 진행을 멈추고 사람 확인을 요구한다
const ratio = groups.length > 0 ? orphanGroups.length / groups.length : 0;
if (articles.length === 0 || ratio > 0.5) {
  return { ...result, requiresConfirmation: true };
}
```

글 0건에서 무조건 예외를 던지는 방법도 있지만, 그러면 글을 아직 한 편도 쓰지 않은 상태에서는
(업로드 후 발행 취소한 글의 이미지 등을) 영영 정리할 수 없게 됩니다. "확인 요구"가 맞습니다.
`deleteOrphanArticleImages`의 재검사도 같은 함수를 다시 부르므로, 이 가드는 scan 쪽에 넣어야 양쪽에 다 걸립니다.

### 3-2. 목록 조회가 1000개에서 조용히 잘린다

**어디에**: `src/lib/supabase/admin-list.ts:27`, `src/lib/supabase/list-crud.ts`

**무엇이 문제인가**

쓰고 있는 DB(Supabase / PostgREST)는 한 번에 최대 1000줄만 돌려줍니다. 그 이상은 오류를 내는 게 아니라 그냥 조용히 잘라서 줍니다.

이 프로젝트는 이미 이 사실을 알고 있습니다. `src/lib/supabase/rag.ts`에 이렇게 적혀 있고, 1000개씩 나눠 읽는 반복문도 있습니다.

```ts
/** PostgREST 서버 기본 max_rows. 이 단위로 Range 페이지네이션한다. */
const PAGE_SIZE = 1000;
```

그런데 관리자 목록 조회에는 그 반복문이 없습니다. 한 번만 물어보고 끝냅니다.

**언제 터지나**

사진이 1000장을 넘는 순간입니다. 관리자 화면에서 뒷부분 사진들이 사라집니다. 오류 메시지도 안 나옵니다.
더 나쁜 건, 이 상태에서 드래그로 순서를 바꾸면 `reorder`가 화면에 보이는 것만 가지고 순서 번호를 0부터 다시 매겨 저장한다는 점입니다. 화면에 없는 사진들의 정렬이 망가집니다.

그리고 이게 위의 3-1 문제를 실제로 일으키는 원인이 될 수 있습니다. 글이 1000편을 넘으면 "쓰고 있는 이미지 목록"이 잘리니까요.

**어떻게 고치나**

`rag.ts`에 이미 있는 Range 반복문을 공용 함수로 빼서 `admin-list.ts`와 `list-crud.ts`에서도 쓰면 됩니다. 새로 만들 게 없습니다.

## 4. 🟠 주의 — 조건이 맞으면 잘못 동작하는 5가지

### 4-1. React 상태 갱신 함수 안에서 ref를 건드린다 (2곳)

**어디에**: `src/features/chat/_hooks/use-chat.ts:133`, `src/features/dev/_components/OnDemandDevProjectDetail.tsx:132`

```ts
setMessages((current) => {
  if (current.length !== 1 || current[0]?.id !== "welcome") return current;
  const next = [createInitialMessage(lang)];
  messagesRef.current = next; // ← 여기가 문제
  return next;
});
```

**왜 문제인가**

`setState(현재값 => 새값)` 안에 넣는 함수는 계산만 하고 아무것도 바꾸지 않아야 한다는 React 규칙이 있습니다.
React는 이 함수를 두 번 부를 수도 있고, 결과를 버릴 수도 있습니다. 개발 모드(StrictMode)에서는 실제로 두 번 부릅니다.

위 코드는 조건이 안 맞으면 `return current`로 일찍 빠져나가서 ref를 안 건드리는 갈래가 있습니다.
결과가 버려지면 화면 상태와 `messagesRef`가 서로 다른 값을 갖게 됩니다.

어긋났을 때 벌어지는 일이 두 곳에서 다릅니다. 방향에 주의해야 합니다.

- `use-chat.ts`는 이 ref로 대화 기록을 만들어 서버에 보냅니다. 어긋나면 화면과 다른 대화 내용이 전송될 수 있습니다.
- `OnDemandDevProjectDetail.tsx`는 ref가 상태보다 **앞서는** 방향으로 어긋납니다 (updater 안에서 ref에 먼저 넣는데 그 결과가 버려지는 경우).
  그러면 "이미 받아왔다"고 잘못 판단해 fetch를 **건너뛰고**, 상태에는 상세 데이터가 없으니
  모달이 스켈레톤에서 멈춥니다. 실패 상태도 아니어서 재시도 버튼조차 안 나옵니다.
  (재호출 낭비가 아니라 미호출 멈춤입니다. 이쪽이 더 나쁩니다.)

**어떻게 고치나**

ref 대입을 `useEffect`로 옮깁니다.

```ts
useEffect(() => {
  setMessages((current) => {
    if (current.length !== 1 || current[0]?.id !== "welcome") return current;
    return [createInitialMessage(lang)];
  });
}, [lang]);

useEffect(() => {
  messagesRef.current = messages; // 상태가 바뀐 뒤에 따라간다
}, [messages]);
```

### 4-2. 챗봇 요청 본문 크기 검사를 우회할 수 있다

**어디에**: `src/features/chat/_lib/handle-chat-request.ts:380~391`

크기 검사가 두 단계인데 순서에 구멍이 있습니다.

```
380줄: Content-Length 헤더를 보고 20KB 넘으면 거절
387줄: await request.text()          ← 본문 전체를 메모리에 올림
391줄: 실제 길이가 20KB 넘으면 거절   ← 이미 다 읽은 뒤
```

`Transfer-Encoding: chunked`로 보내면 `Content-Length` 헤더가 아예 없어서 380줄 검사를 그냥 통과합니다.
그러면 387줄에서 본문 전체(Vercel 상한 4.5MB)를 서버 메모리에 올린 다음에야 거절합니다.

게다가 사용량 제한 검사(`rateLimiter`)는 410줄, 그보다 뒤에 있습니다. 제한에 걸린 사람도 매 요청마다 서버 메모리를 소모시킬 수 있습니다.

참고로 같은 저장소의 Sentry 웹훅(`verifySentrySignature`)은 chunked 경우를 명시적으로 다시 재는 코드가 있습니다. 챗 경로에만 그게 빠져 있습니다.

**어떻게 고치나**: 순서를 바꿉니다. 사용량 제한을 먼저 검사하고, 본문은 스트림으로 읽으면서 20KB를 넘는 순간 중단합니다.

### 4-3. 스트리밍이 끊긴 것과 정상 완료를 구분하지 못한다

**어디에**: `src/features/chat/_lib/sse-stream.ts:31`

```ts
while (!signal.aborted) { ... }   // 중단되면 조용히 빠져나감
```

다행히 대부분의 중단은 여기까지 오지 않습니다. 타임아웃 시그널은 `AbortSignal.any`로 합쳐져
`fetch`에도 같이 전달되기 때문에(`chat-provider.ts:73` → `openai-chat-provider.ts:75`),
읽기를 기다리는 도중에 중단되면 `reader.read()`가 AbortError로 거부되고 예외가 정상적으로 올라가 폴백이 동작합니다.

문제는 좁은 경합 구간입니다. 한 조각을 다 읽은 직후 ~ 다음 반복 조건 검사 사이에 중단이 걸리면,
반복문이 예외 없이 조용히 끝납니다. 그러면 호출한 쪽(`openai-chat-provider.ts:97`)은
`response.completed` 이벤트를 못 받았는데도 지금까지 모은 문자열을 `parseOrSalvageChatResult`로
구제해서, 중간에 잘린 답변을 완성된 답변처럼 내보낼 수 있습니다.

발생 확률은 낮지만, 코드가 "중단 = 예외"라는 계약을 스스로 보장하지 않고 fetch의 부수 효과에
기대고 있다는 게 본질입니다. 부수적으로 `reader`도 `cancel()`이나 `releaseLock()` 없이 남습니다.

**어떻게 고치나**: 반복문을 빠져나온 뒤 `signal.aborted`가 참이면 명시적으로 오류를 던지고, `finally`에서 reader를 정리합니다.

### 4-4. 재검증(revalidate) 요청이 소리 없이 사라진다

**어디에**: `src/lib/cache/request-revalidate.ts:18`

관리자가 저장하면 300밀리초 기다렸다가 "공개 페이지 다시 만들어 줘" 요청을 보냅니다. 짧은 시간에 여러 번 저장할 때 요청이 몰리는 걸 막으려는 의도입니다.

그런데 그 0.3초 안에 탭을 닫거나 다른 페이지로 이동하면 요청이 아예 나가지 않습니다.
실패 기록(`recordRevalidateFailure`)은 `catch` 안에서만 부르는데, 실행 자체가 안 됐으니 `catch`도 안 돕니다. 실패 배너에도 아무 흔적이 없습니다.

결과적으로 공개 페이지는 최대 ISR 주기(1시간) 동안 옛날 내용을 보여주는데, 관리자는 그 사실을 알 방법이 없습니다.

**어떻게 고치나**: 재검증은 `"use server"` 서버 액션(`revalidatePublicPages`)이라 `navigator.sendBeacon`으로는 못 보냅니다 (sendBeacon은 서버 액션 프로토콜을 흉내낼 수 없습니다). 현실적인 방법은 이미 있는 실패 기록을 재활용하는 것입니다.

`pagehide`(또는 `visibilitychange`가 `hidden`이 될 때)에서 대기 중인 tags/paths를
`recordRevalidateFailure`로 동기 기록합니다. localStorage 쓰기는 동기라 페이지가 닫혀도 남고,
다음 관리자 방문 때 기존 실패 배너가 그대로 재시도를 제안합니다. 여유가 되면 같은 시점에
flush도 한 번 시도하고, 성공하면 기록을 지우면 됩니다.

### 4-5. 관리자 쪽 티켓 링크만 정화를 안 한다

**어디에**: `src/lib/supabase/music.ts:45`

같은 데이터를 읽는 함수가 두 개인데 규칙이 다릅니다.

```ts
// 공개용 (public/music.ts:37) — 안전
ticketUrl: normalizePublicHref(data.ticketUrl);

// 관리자용 (music.ts:45) — 원본 그대로
ticketUrl: (d.ticketUrl as string) ?? "";
```

`normalizePublicHref`는 `javascript:` 같은 위험한 주소를 막는 함수입니다. 관리자 쪽은 그냥 통과시킵니다.

혼자 쓰는 관리자 화면이라 당장 위험하진 않습니다. 다만 `migrate-image-thumbnails`처럼 문서 전체를 다시 저장하는 코드를 타면, 정화되지 않은 값이 DB에 그대로 다시 쓰입니다. 관리자 화면이 그 값을 링크로 그리는 순간 방어선이 사라집니다.

**어떻게 고치나**: 관리자 디코더에도 같은 함수를 붙입니다. 한 줄입니다.

## 5. 🟡 개선 — 성능 관련 4가지

### 5-1. 블로그 목록이 모든 글의 본문을 통째로 받아 온다

**어디에**: `src/lib/content/dev-articles.ts:37` (본문까지 포함하는 select 정의는 `src/constants/collections.ts:61`)

`getDevArticleBySlug`는 `getDevArticles()`로 전체 글을 본문(`data`)까지 다 받아온 다음 `find`로 한 편을 고릅니다.
이 경로를 목록 페이지, `sitemap.ts`, `generateStaticParams`, 검색이 전부 씁니다.

글 100편에 평균 20KB면, 페이지를 다시 만들 때마다 2MB를 읽습니다. 정작 목록에는 본문이 필요 없습니다.

같은 파일에 본문을 뺀 조회 방식이 이미 있습니다 (`CHAT_ARTICLE_SELECT`, `PROJECT_LINK_SELECT`). 목록과 상세 경로만 그 패턴을 안 쓰고 있습니다.

**어떻게 고치나**: 목록용 조회(본문 제외)와 상세용 조회(slug로 한 건만)를 나눕니다.

**후속 검토 결과 (2026-08-20 구현 시점)** — 이 항목만 **보류**했습니다. 나머지 13건은 반영했습니다.

단순히 조회를 나누면 오히려 요청이 늘어납니다.

1. **slug 단건 조회 추가는 순증가입니다.** 상세 페이지는 이웃 글 표와 BlogTools 때문에 같은 렌더에서
   `getDevArticles()`를 어차피 호출합니다. React `cache` 덕에 지금은 렌더당 목록 조회가 1회인데,
   단건 조회를 더하면 목록 1회 + 단건 1회가 됩니다.
2. **sitemap·generateStaticParams용 slim 조회도 순증가입니다.** `transport.ts`가 fetch에 태그와
   revalidate를 걸어 두어, 전체 목록 조회는 빌드/ISR 전체가 공유하는 Data Cache 엔트리 하나입니다.
   그 둘은 지금 그 캐시를 얻어 타고 있고, select가 다른 slim 조회는 별도 엔트리가 **추가**될 뿐입니다.

진짜 비용은 조회 횟수가 아니라 **매 글 페이지마다 전 글의 마크다운을 파싱**하는 `toArticleToolData`
쪽입니다. 그래서 이 항목은 다음 셋을 한 묶음으로 처리해야 합니다.

- `readingMinutes`·`headings`를 `body` 파생이 아니라 저장 시 계산해 두는 필드로 승격
- 그 뒤에 목록 조회에서 `body` 제외
- 그 뒤에 상세를 slug 단건 조회로 전환

---

### 5-2. 스트리밍 파싱이 글자 수의 제곱만큼 느려진다

**어디에**: `src/features/chat/_lib/chat-response-contract.ts:181`

챗 응답이 조각조각 도착할 때마다, 지금까지 받은 문자열 전체를 처음부터 한 글자씩 다시 훑습니다.

```
조각 1개 도착 → 100자 검사
조각 2개 도착 → 200자 검사 (앞 100자 또 검사)
조각 3개 도착 → 300자 검사
...
```

응답이 4000자이고 조각이 500개면 문자 붙이기가 약 200만 번 일어납니다. 답변이 길수록 서버 CPU 시간이 급격히 늘어서 60초 제한을 갉아먹습니다.

**어떻게 고치나**: 마지막으로 검사한 위치를 기억해 두고 새로 온 부분만 검사합니다.

---

### 5-3. 이미지 업로드가 원본을 세 번 동시에 푼다

**어디에**: `src/features/image-upload/_hooks/use-image-upload.ts:46`

```ts
const [compressed, preview, thumbnail] = await Promise.all([
  compressToWebp(file), // 원본 → 2048px
  compressPreviewToWebp(file), // 원본 → 960px
  compressThumbnailToWebp(file), // 원본 → 320px
]);
```

셋 다 같은 원본 파일을 받습니다. 웹 워커 3개가 동시에 원본을 디코딩하니 메모리가 3배로 듭니다.

4천만 화소 JPEG 한 장이면 워커마다 100MB 이상 잡습니다. 모바일 사파리에서는 탭이 종료되면서 업로드가 실패할 수 있습니다.

**어떻게 고치나**: 2048px를 먼저 만들고, 거기서 960px와 320px를 뽑습니다. 디코딩이 한 번으로 줄고 화질 차이도 사실상 없습니다.

```ts
const compressed = await compressToWebp(file);
const [preview, thumbnail] = await Promise.all([
  compressPreviewToWebp(compressed),
  compressThumbnailToWebp(compressed),
]);
```

### 반영하면서 달라진 것

구현 중 세 항목은 제안한 방법 그대로는 다른 문제를 만들어 방향을 바꿨습니다.

- **6번 티켓 링크**: 읽기 시점에 정화하면 `http://` 주소가 빈 값이 되고, 폼 검증이 빈 값을 통과시켜
  무관한 필드만 고쳐 저장해도 원래 주소가 사라집니다. 이미지 마이그레이션은 폼을 거치지 않아 같은
  값을 지웁니다. 읽기는 원본을 보존하고, 저장 경계에서 실행 가능한 스킴만 막는 쪽으로 바꿨습니다.
  https 전용 정책은 기존 폼 검증이 그대로 봅니다.
- **5번 ref 대입**: `use-chat.ts` 는 다른 경로에서 ref 가 상태를 앞서는 모델을 씁니다. 동기화
  `useEffect` 를 얹으면 한 파일에 상반된 소유 모델이 생겨, 대신 lang 효과만 같은 모델로 맞췄습니다.
- **3번 페이지네이션**: 관리자 목록뿐 아니라 공개 읽기 경로에도 같은 절단이 있어 함께 고쳤습니다.

반영 뒤 두 차례 검수에서 회귀와 계약 미비가 더 나왔고, 후속 커밋 16개로 닫았습니다.
어떤 문제를 어떻게 고쳤는지는 각 커밋 메시지에 적혀 있습니다.
