# 브라우저 언어 기반 최초 진입 라우팅 계획

> 상태: **구현 완료 / 로컬 검증 완료 / 배포 검증 완료**
> 대상: 언어 프리픽스가 없는 루트 URL `/`
> 목적: 한국어가 아닌 브라우저의 해외 방문자를 영어 랜딩 `/en`으로 안내하면서 사용자 선택권, SEO, 캐시 안정성을 보존한다.
> 관련 결정: [ADR-0002 경로 기반 i18n](../adr/0002-path-based-i18n.md)

## 1. 요약

개정 전에도 공개 페이지는 `/ko/*`와 `/en/*`로 분리되어 있었지만, 언어가 없는 URL은
`next.config.ts`의 영구 리다이렉트로 `/ko/*`에 연결됐다. 따라서 영어 콘텐츠가 있어도 도메인
루트로 들어온 해외 방문자는 먼저 한국어 페이지를 보게 됐다.

이 계획은 `/` 요청에 한해서 다음 우선순위로 목적지를 선택한다.

1. 사용자가 언어 메뉴에서 명시적으로 선택한 쿠키
2. 요청의 `Accept-Language`
3. 언어 정보를 확인할 수 없을 때의 기본값 `ko`

결과가 요청마다 달라질 수 있으므로 영구 리다이렉트가 아닌 `307 Temporary Redirect`를 사용한다.
명시적인 `/ko/*`와 `/en/*` URL은 브라우저 언어 또는 쿠키와 관계없이 그대로 제공한다.

```text
GET /
  │
  ├─ 유효한 언어 선택 쿠키가 있는가?
  │    ├─ ko → 307 /ko
  │    └─ en → 307 /en
  │
  ├─ Accept-Language가 있는가?
  │    ├─ 최우선 언어가 ko 계열 → 307 /ko
  │    └─ 그 밖의 언어         → 307 /en
  │
  └─ 헤더가 없거나 해석 불가 → 307 /ko
```

## 2. 배경과 개정 전 구조

### 2.1 이미 갖춘 기반

- 공개 URL은 `app/[lang]/(public)` 아래의 `/ko/*`, `/en/*`로 분리되어 있다.
- URL의 `[lang]` 세그먼트가 공개 페이지 표시 언어의 단일 출처다.
- 각 언어 페이지는 자기 자신을 canonical로 사용한다.
- 모든 공개 페이지와 sitemap에 `ko`, `en`, `x-default` hreflang이 있다.
- 언어 메뉴는 같은 페이지의 반대 언어 URL로 이동한다.
- 언어 선택은 `ap-lang:v1` localStorage에 저장된다.
- 번역 값이 비어 있으면 `pickText`가 `현재 언어 → en → ko` 순서로 폴백한다.

### 2.2 개정 전 문제

`next.config.ts`에는 다음과 같은 결정적 308 리다이렉트가 있다.

```text
/              → /ko
/photo/*       → /ko/photo/*
/music/*       → /ko/music/*
/dev/*         → /ko/dev/*
그 밖의 구 URL → 대응하는 /ko/*
```

이 구성은 검색엔진과 캐시 관점에서 단순하지만, 도메인 루트로 유입되는 비한국어 방문자에게
영어 버전을 자동으로 제시하지 못한다. 또한 localStorage는 서버 요청에 포함되지 않기 때문에,
서버가 기존 사용자 선택을 우선할 방법이 없다.

## 3. 목표와 비목표

### 목표

- 한국어가 아닌 브라우저의 `/` 최초 방문을 `/en`으로 안내한다.
- 사용자가 명시적으로 선택한 언어를 브라우저 기본 언어보다 우선한다.
- `/ko/*`와 `/en/*`를 안정적이고 직접 접근 가능한 URL로 유지한다.
- Googlebot처럼 언어 헤더가 없는 요청에 결정적인 기본값을 제공한다.
- 잘못 공유된 CDN 캐시, 리다이렉트 루프, 쿼리 유실을 방지한다.
- 영어 자동 유입 증가에 앞서 번역 누락을 발견할 수 있게 한다.
- 문제 발생 시 즉시 기존 `/ → /ko` 정책으로 되돌릴 수 있게 한다.

### 비목표

- IP 주소나 접속 국가를 이용한 지역 판별
- `/ko/*` 방문자를 브라우저 언어 때문에 `/en/*`로 강제 전환
- `/en/*` 방문자를 쿠키나 브라우저 언어 때문에 `/ko/*`로 강제 전환
- 관리자와 API 경로의 국제화
- 프랑스어·일본어 등 세 번째 언어 지원
- 언어별 도메인 분리
- 번역 생성 또는 기존 번역의 자동 보정
- 광고 개인화·리마케팅·Google Ads 연동
- Advanced Consent Mode의 cookieless ping과 모델링

## 4. 확정할 라우팅 정책

### 4.1 판정 우선순위

| 순위 | 신호                            | 처리                                                         |
| ---: | ------------------------------- | ------------------------------------------------------------ |
|    1 | URL에 `/ko` 또는 `/en`이 명시됨 | URL을 그대로 존중하고 자동 리다이렉트하지 않는다.            |
|    2 | 유효한 언어 선택 쿠키           | 쿠키의 `ko` 또는 `en`으로 보낸다.                            |
|    3 | 유효한 `Accept-Language`        | 최우선 언어가 `ko` 계열이면 `ko`, 그 외에는 `en`으로 보낸다. |
|    4 | 헤더 없음·빈 값·해석 실패       | `ko`로 보낸다.                                               |

여기서 “최우선 언어”는 단순히 문자열의 첫 토큰을 자르는 것이 아니라 품질값(`q`)을 반영해
정렬된 브라우저 선호 언어를 뜻한다. `ko`, `ko-KR` 등 언어 코드가 `ko`인 로케일은 모두
한국어로 취급한다.

예시는 다음과 같다.

| 요청 신호                                  | 결과            |
| ------------------------------------------ | --------------- |
| `Accept-Language: ko-KR,ko;q=0.9,en;q=0.8` | `/ko`           |
| `Accept-Language: en-US,en;q=0.9,ko;q=0.8` | `/en`           |
| `Accept-Language: ja-JP,ja;q=0.9,en;q=0.8` | `/en`           |
| `Accept-Language: fr-FR`                   | `/en`           |
| `Accept-Language` 없음                     | `/ko`           |
| 영어 헤더 + `ko` 선택 쿠키                 | `/ko`           |
| 한국어 헤더 + `en` 선택 쿠키               | `/en`           |
| 영어 헤더 + `/ko/photo` 요청               | 리다이렉트 없음 |
| 한국어 헤더 + `/en/dev` 요청               | 리다이렉트 없음 |

### 4.2 적용 경로

1차 적용 범위는 `/` 하나로 제한한다. Next.js Proxy의 matcher도 가능하면 `/`만 실행되게 한다.
이렇게 하면 `/_next`, 정적 파일, `/api`, `/admin`, sitemap, robots 및 이미 로컬라이즈된 공개
경로가 판정 로직을 통과하지 않는다.

`/photo`, `/music`, `/dev`, `/albums`, `/about` 등은 과거 URL의 검색 신호와 외부 링크를
정리하는 마이그레이션 경로다. 이 계획에서는 기존의 결정적인 `/ko/*` 308을 유지한다. 해외
캠페인, 영문 SNS 및 영문 문서에서는 무언어 구 URL 대신 `/en/*`를 직접 링크한다.

추후 무언어 구 URL도 언어 감지 대상으로 넓히려면 별도의 SEO 영향 검토와 리다이렉트 매핑
테스트를 선행한다. 최초 구현 범위에 섞지 않는다.

## 5. 구현 설계

### 5.1 서버 진입점

Next.js 16의 `proxy.ts`에서 `/` 요청을 처리한다.

- `next.config.ts`의 `/ → /ko` 규칙만 제거한다.
- 나머지 구 URL 308 규칙은 그대로 둔다.
- Proxy는 쿠키와 `Accept-Language`를 읽고 목적지를 결정한다.
- 원래 URL의 query string을 목적지에 그대로 보존한다.
- 응답은 `307 Temporary Redirect`로 반환한다.
- Proxy matcher는 `/`로 한정한다.

`next.config.ts` 리다이렉트는 Proxy보다 먼저 평가될 수 있으므로 기존 `/ → /ko` 규칙을
남겨 둔 채 Proxy만 추가해서는 안 된다. 이 경우 언어 판정 코드까지 요청이 도달하지 않는다.

### 5.2 `Accept-Language` 해석

헤더는 외부 입력이므로 다음 조건을 만족해야 한다.

- 품질값(`q`)과 지역 코드가 정상 처리돼야 한다.
- 대소문자 차이를 허용한다.
- 비정상 값에서 예외를 외부로 전파하지 않는다.
- 처리할 헤더는 최대 512자로 제한하고 검증된 파서를 사용한다.
- 파서 결과는 반드시 `ko | en | default` 중 하나로 정규화하고, 최종 라우팅 결과는 `ko | en`으로 제한한다.

`negotiator`를 직접 Proxy 컴포넌트에 흩어 쓰지 않고, 최대 길이 검사·예외 처리·제품 정책 정규화를
담당하는 순수 함수 뒤에 둔다. 라이브러리 반환값이 곧 서비스 언어가 되는 것이 아니라, 정렬된 최우선
구체 언어가 `ko` 계열인지 판정하는 입력으로만 사용한다. 타입 선언 패키지가 필요하면 런타임
`negotiator`와 함께 npm 10 lockfile 절차로 추가한다.

제품 규칙은 “지원 언어 중 가장 가까운 언어”가 아니라 “사용자의 최우선 브라우저 언어가
한국어인가”이다. 따라서 최우선 언어가 일본어이고 낮은 우선순위에 한국어가 있더라도 결과는
`en`이다. 이 규칙을 바꾸려면 테스트 표와 제품 문서를 함께 수정해야 한다.

### 5.3 언어 선택 쿠키

현재 localStorage 키 `ap-lang:v1`은 유지하고, 서버가 읽을 수 있는 기능성 쿠키를 추가한다.
쿠키 이름은 `ap-lang-pref-v1`으로 정하고 상수 한 곳에서 관리한다. 계약은 다음과 같다.

| 속성       | 값                | 이유                                                         |
| ---------- | ----------------- | ------------------------------------------------------------ |
| 이름       | `ap-lang-pref-v1` | localStorage와 목적을 구분하고 버전을 명시한다.              |
| 값         | `ko` 또는 `en`    | 허용값을 최소화한다.                                         |
| `Path`     | `/`               | 루트 요청과 모든 공개 경로에서 일관되게 사용한다.            |
| `Max-Age`  | `2592000`초(30일) | 선호를 유지하되 기능성 쿠키 보유 기간을 보수적으로 제한한다. |
| `SameSite` | `Lax`             | 일반적인 자사 기능성 쿠키에 충분하다.                        |
| `Secure`   | 운영에서 활성화   | HTTPS에서만 전송한다.                                        |
| `HttpOnly` | 사용하지 않음     | 현재 클라이언트 언어 메뉴가 직접 갱신해야 한다.              |

쿠키에는 언어 코드 외의 사용자 정보, 원본 `Accept-Language`, IP 또는 분석 식별자를 넣지 않는다.
쿠키/개인정보 안내에 이름, 목적, 값, 보유 기간과 삭제 방법을 명시한다.

쿠키는 `/` 자동 판정 과정에서 만들지 않는다. 사용자가 언어 메뉴에서 `한국어` 또는 `English`를
직접 선택한 경우에만 저장한다. 단순 페이지 방문을 언어 저장 동의로 간주하지 않으며, 언어 쿠키를
분석·광고·세션 식별에 재사용하지 않는다. 보유 기간을 늘리려면 실제 사용자 기대와 적용 국가의
규정을 다시 검토한다.

언어 메뉴에서 사용자가 선택할 때 다음 작업을 한 이벤트 안에서 수행한다.

1. 기존 localStorage 갱신
2. 언어 쿠키 갱신
3. 같은 페이지의 선택 언어 URL로 클라이언트 내비게이션

쿠키 쓰기가 실패해도 현재 페이지의 언어 전환은 성공해야 한다. 이 경우 다음 `/` 방문에서는
브라우저 언어 판정으로 돌아간다.

기존 localStorage 사용자에게는 서버 요청 전에 값을 전달할 방법이 없다. 첫 배포 시점에 이미
저장된 localStorage를 쿠키로 한 번 마이그레이션할 수 있지만, 그 사용자의 첫 `/` 요청에는
적용되지 않는다. 복잡도를 줄이려면 이후 언어 메뉴 선택부터 쿠키를 기록하고, 기존 사용자에게는
페이지의 언어 메뉴를 계속 제공하는 점진 이행을 허용한다.

### 5.4 응답 상태와 캐시

언어 판정 결과는 요청 헤더와 쿠키에 따라 달라지므로 `308 Permanent Redirect`를 사용하지 않는다.
`307`은 요청이 임시로 다른 위치에 연결되며 원래 HTTP 메서드를 보존한다. 실제 적용 대상은 공개
랜딩의 `GET`과 `HEAD`로 한정한다.

루트 리다이렉트 응답에는 다음 캐시 정책을 권장한다.

```http
Cache-Control: private, no-store
```

`Vary: Accept-Language, Cookie`로 공유 캐시를 분기할 수도 있지만, 전체 Cookie 값은 조합 수가 많아
캐시 효율과 운영 가시성을 떨어뜨린다. `/`의 짧은 리다이렉트 한 건은 캐시하지 않는 편이 단순하고
안전하다. 배포 환경이 응답 헤더를 덮어쓰는지 실제 Vercel 응답으로 확인한다.

### 5.5 URL 보존

Proxy는 query string을 반드시 유지한다.

```text
/?utm_source=instagram&utm_campaign=profile
→ /en?utm_source=instagram&utm_campaign=profile
```

URL fragment(`#...`)는 서버 요청에 포함되지 않으므로 서버 코드가 직접 읽을 수 없다. 브라우저가
리다이렉트 후 fragment를 유지하는지는 대상 브라우저에서 확인하며, 랜딩의 핵심 동작이나 분석을
fragment 보존에 의존시키지 않는다.

## 6. 위험별 대응

### 6.1 검색엔진이 한 언어만 발견하는 문제

- 자동 판정은 언어가 없는 `/`에만 적용한다.
- `/ko/*`, `/en/*`는 항상 직접 접근 가능하게 둔다.
- 모든 언어 URL을 sitemap과 hreflang으로 상호 연결한다.
- 헤더가 없는 요청은 `x-default`와 같은 `ko`로 결정한다.
- 검색봇 전용 분기나 User-Agent 기반 예외를 만들지 않는다.
- canonical은 리다이렉트 전 `/`이 아니라 각 언어 페이지 자기 자신을 유지한다.

### 6.2 사용자 선택이 브라우저 설정에 덮이는 문제

- 명시적 URL을 최우선으로 존중한다.
- 언어 메뉴 선택을 localStorage와 쿠키에 함께 기록한다.
- 쿠키가 있으면 `Accept-Language`를 보지 않는다.
- 모든 공개 페이지에서 언어 메뉴를 유지한다.

### 6.3 한 사용자의 리다이렉트가 다른 사용자에게 캐시되는 문제

- 루트 리다이렉트에 `private, no-store`를 적용한다.
- 배포 후 한국어·영어 헤더로 실제 응답을 각각 요청해 목적지와 캐시 헤더를 확인한다.
- CDN 캐시 제거 후에도 결과가 같아야 한다.

### 6.4 기존 308이 브라우저에 남는 문제

기존 `/ → /ko`는 영구 리다이렉트이므로 일부 재방문 브라우저가 서버에 다시 묻지 않고 `/ko`로
갈 수 있다. 서버에서 이미 저장된 브라우저 리다이렉트 캐시를 강제로 지울 수는 없다.

- 배포 시 Vercel/CDN 캐시는 제거한다.
- 영문 공유 링크와 외부 프로필은 `/en`을 직접 사용한다.
- `/ko`에서도 언어 메뉴를 쉽게 찾을 수 있게 유지한다.
- 신규 방문과 시크릿 창에서 새 정책을 우선 검증한다.
- 전환율 평가는 배포 직후의 기존 사용자 캐시 영향을 감안한다.

### 6.5 영어 콘텐츠가 한국어로 폴백하는 문제

자동 영어 유입 전에 주요 공개 콘텐츠의 `en` 필드 누락을 점검한다.

최소 검사 대상:

- 랜딩 이름, 태그라인, 소개 문구
- 전역 navigation과 연락 문구
- Dev 프로젝트 제목·요약·본문·트러블슈팅
- Music 작업·경력·소개
- Photo 제목·앨범·태그·장소·소개
- 페이지 title, description 및 이미지 대체 텍스트

초기에는 현재 `pickText` 폴백을 유지해 화면이 비는 것을 막는다. 이후 관리자 화면 또는 검증
스크립트에 `완료 / 일부 누락 / 전체 누락` 상태를 제공한다. 핵심 SEO 필드의 영어 값이 비어 있으면
게시 또는 운영 점검 단계에서 경고하는 것이 바람직하다.

### 6.6 리다이렉트 루프와 잘못된 경로 개입

- Proxy matcher를 `/` 하나로 제한한다.
- 목적지가 이미 `/ko` 또는 `/en`이면 다시 판정하지 않는다.
- `/admin`, `/api`, `/_next`, 정적 파일에는 Proxy를 실행하지 않는다.
- `next.config.ts`의 `/` 규칙을 제거해 이중 리다이렉트를 막는다.
- 목적지는 내부의 고정된 `/ko`, `/en`만 허용해 open redirect를 만들지 않는다.

### 6.7 분석 데이터가 왜곡되는 문제

리다이렉트 자체를 페이지뷰로 중복 기록하지 않는다. 최종 `/ko` 또는 `/en` 랜딩의 페이지뷰만
기존 GA 흐름으로 측정한다. 필요한 경우 원본 헤더 전체가 아니라 다음 정규화 값만 별도 이벤트로
기록한다.

- 선택된 언어: `ko | en`
- 판정 출처: `cookie | accept-language | default`

IP, 원본 `Accept-Language` 전체 문자열 또는 쿠키 원문은 분석 이벤트에 보내지 않는다. 배포 전후에는
언어별 랜딩 유입, 이탈률, 언어 메뉴 재전환 비율을 비교한다. `/en`으로 들어온 직후 `/ko`를 선택하는
비율이 높으면 감지 규칙 또는 영어 콘텐츠 품질을 재검토한다.

### 6.8 쿠키 고지와 동의 범위를 혼동하는 문제

이 계획의 언어 선호 쿠키와 GA4 분석 쿠키는 목적과 법적 판단을 분리한다. 쿠키라는 기술 형식이
같다는 이유로 하나의 동의 상태나 하나의 저장값에 묶지 않는다. localStorage도 사용자의 단말에
정보를 저장하는 기술이므로, 쿠키 이름만 피한다고 동의·고지 검토가 사라지는 것은 아니다.

#### 언어 선호 쿠키

다음 조건을 모두 지키면 별도의 사이트 진입 쿠키 배너에서 사전 수락을 요구하지 않고 기능성 또는
사용자 요청 기반 저장으로 운영할 근거가 강하다.

- 사용자가 언어 메뉴를 직접 선택한 뒤에만 저장한다.
- 값은 `ko | en`이고 언어 선택을 기억하는 목적으로만 사용한다.
- first-party이며 광고, 분석, 사용자 식별 또는 다른 데이터와의 결합에 사용하지 않는다.
- 보유 기간을 초기 30일로 제한한다.
- 사용자가 언제든 반대 언어를 선택해 값을 바꿀 수 있고, 브라우저에서 삭제해도 사이트 이용이
  가능하다.
- 쿠키/개인정보 안내에 이름, 목적, 값, 보유 기간, 삭제 방법을 공개한다.

언어 선택 UI 가까이에 “선택한 언어를 30일간 기억합니다”와 같은 짧은 안내를 제공하면 사용자의
클릭이 무엇을 저장하는지 더 명확해진다. 이 안내는 사이트 전체를 막는 수락 배너가 아니라 언어
선택 기능에 붙는 문맥상 고지다.

EU ePrivacy의 과거 Article 29 Working Party 의견은 사용자 인터페이스 맞춤 쿠키를 일정 조건에서
동의 면제 가능 사례로 보지만, 보유 기간과 사용자의 명시적 요청을 중요하게 본다. 영국 ICO도 언어
선호 쿠키를 면제 가능성이 있는 UI 맞춤 사례로 설명하고 실제 사이트에서 essential cookie로
분류한다. 다만 국가별 구현법과 최신 해석이 다를 수 있으므로 이 문서는 법률 자문을 대체하지 않는다.

한국에서는 모든 쿠키에 일률적으로 사전 수락 배너를 요구한다고 단정할 수 없다. 해당 값이 다른
정보와 결합되어 개인을 식별하거나 행태 분석에 사용되는지, 처리 근거와 고지가 적절한지를 목적별로
판단해야 한다. 이 언어 값은 추적 식별자와 결합하지 않고 개인정보/쿠키 안내에 자동 수집·저장 장치의
목적과 거부 방법을 명시하는 보수적 운영을 택한다.

#### `Accept-Language`

`Accept-Language`는 브라우저가 HTTP 요청에 보내는 헤더이며 이 기능이 새 쿠키를 생성하는 것은
아니다. 서버는 `ko | en | default` 판정에만 사용하고 원문을 DB, 쿠키 또는 분석 이벤트에 저장하지
않는다. 다른 브라우저 특성과 결합해 fingerprinting에 사용하지 않는다.

#### GA4 분석 쿠키

GA4는 언어 기억에 필요하지 않은 별도 분석 기능이다. 개정 전 `GoogleAnalytics` 컴포넌트는 측정
ID가 있으면 방문자의 선택을 확인하기 전에 Google tag를 로드했다. EU·영국 등에서는 분석 저장이
일반적으로 필수 쿠키 면제에 포함되지 않으므로, 현재 구현은 Google tag를 명시적 허용 뒤에만
불러온다.

확정한 운영안은 다음과 같다.

1. 분석 동의 전에는 Google tag 자체를 로드하지 않는 Basic Consent Mode를 사용한다.
2. `분석 허용`과 `거부`를 한 화면에서 같은 클릭 수로 제공하고, 거부해도 사이트 전체를 이용할 수
   있게 한다.
3. 동의 선택은 언어 쿠키와 별도인 `ap-analytics-consent:v1` localStorage에
   `{ value: "granted" | "denied", expiresAt }` 형태로 180일간 저장한다.
4. 동의 철회 UI와 개인정보/쿠키 안내를 제공한다.
5. 언어 선호 쿠키는 분석 동의를 거부해도 정상 동작하게 한다.

Google Consent Mode는 사용자의 선택을 Google tag에 전달하는 기술이지, 그 자체가 동의를 받아주는
배너는 아니다. 따라서 사이트가 직접 동의 UI와 저장·철회 기능을 제공한다. Basic Consent Mode를
선택했으므로 분석에 동의하기 전에는 Google tag를 로드하거나 Google로 cookieless ping을 보내지
않는다.

첫 방문에는 현재 URL 언어로 된 하단 동의 배너를 표시한다. `분석 허용`과 `거부`는 한 화면에서 바로
선택할 수 있고 키보드로도 조작할 수 있으며, Privacy 링크를 함께 제공한다. Footer의 `개인정보 및
쿠키 설정`에서 언제든 선택을 다시 열 수 있게 한다. 저장값이 없거나 만료·손상됐으면 미동의 상태로
보고 배너를 다시 표시한다. 동의 철회 시 이후 GA 이벤트와 신규 tag 로드를 중단하며, 가능하면 이
사이트가 만든 GA 쿠키도 제거한다.

#### Privacy 페이지

`/ko/privacy`와 `/en/privacy`는 최소한 다음 내용을 같은 의미로 제공한다.

- 운영자와 문의 수단
- 처리하는 데이터와 목적: 서버 요청 로그, `Accept-Language`, 언어 선호 저장, GA4, 챗봇 요청
- 언어 쿠키 `ap-lang-pref-v1`의 값, 목적, 30일 보유 기간과 삭제 방법
- 분석 동의 저장값의 이름, 목적, 보유 기간과 변경·철회 방법
- 분석 동의 전에는 GA tag가 로드되지 않는다는 설명
- Google Analytics의 처리 주체, 전송 범위와 관련 정책 링크
- 문의 제출을 처리하는 Web3Forms의 최대 보유 기간과 정책 링크
- 챗봇 제공자 전송, 애플리케이션 상태와 남용 방지 로그의 보관 차이, 민감정보 입력 금지 안내
- 브라우저 쿠키·localStorage 삭제 방법
- 개인정보 관련 문의 방법과 문서 시행일·변경 이력

Privacy 페이지는 법률 문구를 과도하게 단정하지 않고 실제 코드 동작과 일치해야 한다. GA, 챗봇,
저장 기간 또는 제공자가 바뀌면 코드와 같은 변경에서 갱신한다. Footer 또는 동일하게 지속 노출되는
공개 navigation에서 접근할 수 있게 하며, 분석 동의 UI에서도 직접 링크한다.

## 7. 테스트 계획

가능한 문자열을 사례별로 끝없이 나열하는 대신 입력을 동치분할하고 경계값, 조합, 불변 속성을
검증한다. 언어 파싱, 정책 판정, HTTP 응답, 클라이언트 저장을 서로 분리해 실패 원인을 좁힐 수 있게
한다.

### 7.1 `Accept-Language` 파서 단위 테스트

파서 계약은 다음과 같이 고정한다.

- `q=0` 항목은 사용자가 수락하지 않는 언어이므로 후보에서 제외한다.
- `*`는 구체적인 언어가 아니므로 최우선 언어 판정에서 제외한다.
- 유효한 구체 언어 중 `q`가 가장 높은 항목을 사용한다.
- 같은 `q`이면 헤더에 먼저 나온 항목을 사용한다.
- 잘못된 항목은 건너뛰고 남은 유효 항목으로 판정한다.
- 유효한 구체 언어가 하나도 없으면 `default`로 판정한다.
- 512자를 넘는 헤더는 파싱하지 않고 `default`로 판정한다.
- 결과는 `ko | en | default` 외의 값을 반환하지 않고 절대 예외를 던지지 않는다.

#### 정상 언어 코드

| 헤더         | 기대 |
| ------------ | ---- |
| `ko`         | `ko` |
| `KO`         | `ko` |
| `ko-KR`      | `ko` |
| `ko-kore-kr` | `ko` |
| `en`         | `en` |
| `en-US`      | `en` |
| `en-GB`      | `en` |
| `ja`         | `en` |
| `ja-JP`      | `en` |
| `fr-FR`      | `en` |
| `zh-Hans-CN` | `en` |

지원하지 않는 구체 언어는 “헤더 없음”이 아니라 비한국어 선호이므로 `en`으로 판정한다.

#### 품질값과 순서

| 헤더                       | 기대      | 이유                                        |
| -------------------------- | --------- | ------------------------------------------- |
| `ko-KR,ko;q=0.9,en;q=0.8`  | `ko`      | 한국어가 최우선이다.                        |
| `en-US,en;q=0.9,ko;q=0.8`  | `en`      | 영어가 최우선이다.                          |
| `en;q=0.4,ko;q=0.9`        | `ko`      | 문자열 순서보다 `q`가 우선한다.             |
| `ko;q=0.4,en;q=0.9`        | `en`      | 문자열 순서보다 `q`가 우선한다.             |
| `ja;q=1,ko;q=0.9,en;q=0.8` | `en`      | 최우선 언어가 일본어다.                     |
| `ja;q=0.5,ko;q=0.5`        | `en`      | 같은 `q`에서는 먼저 나온 일본어가 우선한다. |
| `ko;q=0.5,ja;q=0.5`        | `ko`      | 같은 `q`에서는 먼저 나온 한국어가 우선한다. |
| `ko;q=1.0`                 | `ko`      | 상한 경계값을 허용한다.                     |
| `en;q=0.001,ko;q=0`        | `en`      | 양수 최소 경계와 거부 항목을 구분한다.      |
| `ko;q=0,en;q=1`            | `en`      | 거부된 한국어를 제외한다.                   |
| `ko;q=0`                   | `default` | 수락 가능한 구체 언어가 없다.               |

#### 공백·중복·와일드카드

| 헤더                   | 기대      |
| ---------------------- | --------- |
| `ko-KR , en ; q=0.8`   | `ko`      |
| `en,en-US;q=0.9`       | `en`      |
| `ko;q=0.7,ko-KR;q=0.9` | `ko`      |
| `*,ko;q=0.9`           | `ko`      |
| `*`                    | `default` |
| `*;q=0`                | `default` |
| `,ko,,en;q=0.5,`       | `ko`      |

빈 목록 항목은 건너뛰는 관대한 파싱을 계약으로 정한다. 중요한 불변 조건은 예외가 없고 결과가
허용된 세 값 중 하나라는 점이다.

#### 누락·비정상·공격성 입력

| 헤더                     | 기대                                      |
| ------------------------ | ----------------------------------------- |
| 헤더 없음                | `default`                                 |
| 빈 문자열                | `default`                                 |
| 공백만 존재              | `default`                                 |
| `;;;;`                   | `default`                                 |
| `q=0.9`                  | `default`                                 |
| `ko;q=abc`               | 잘못된 항목 제외 후 `default`             |
| `ko;q=-1`                | 잘못된 항목 제외 후 `default`             |
| `ko;q=1.1`               | 잘못된 항목 제외 후 `default`             |
| `ko;q=0.1234`            | 파서가 허용하지 않으면 제외, 예외 없음    |
| `ko;q=abc,en;q=0.8`      | `en`                                      |
| NUL·제어문자 포함 값     | 예외 없이 `default` 또는 유효 항목만 사용 |
| 512자와 정확히 같은 값   | 정상 파싱                                 |
| 513자 값                 | `default`                                 |
| 수천 개의 쉼표·중복 항목 | 제한 시간 안에 종료하고 예외 없음         |

### 7.2 정책 판정 순수 함수 테스트

파싱과 별개로 `cookie + parsed browser preference → locale` 우선순위를 검증한다.

| 쿠키                   | 브라우저 판정 | 기대 결과 | 판정 출처         |
| ---------------------- | ------------- | --------- | ----------------- |
| `ko`                   | `en`          | `ko`      | `cookie`          |
| `en`                   | `ko`          | `en`      | `cookie`          |
| `ko`                   | `default`     | `ko`      | `cookie`          |
| `en`                   | `default`     | `en`      | `cookie`          |
| 없음                   | `ko`          | `ko`      | `accept-language` |
| 없음                   | `en`          | `en`      | `accept-language` |
| 없음                   | `default`     | `ko`      | `default`         |
| 빈 값                  | `en`          | `en`      | `accept-language` |
| `fr`                   | `ko`          | `ko`      | `accept-language` |
| `KO`                   | `en`          | `en`      | `accept-language` |
| `en-US`                | `ko`          | `ko`      | `accept-language` |
| URL 인코딩 값 `%65%6e` | `ko`          | `ko`      | `accept-language` |

쿠키 값은 정확히 `ko` 또는 `en`만 허용한다. 대소문자, 공백, 지역 코드, URL 인코딩 값을 관대하게
받지 않아 쿠키 계약을 단순하게 유지한다. 잘못된 쿠키는 삭제를 시도하지 않고 해당 요청에서 무시한다.

추가 경계:

- 쿠키가 만료되면 브라우저가 보내지 않으므로 “없음”과 같아야 한다.
- 같은 이름의 쿠키가 둘 이상이면 순서에 의존하지 않고 모두 무시한 뒤 헤더로 판정한다.
- 다른 쿠키가 수십 개 있어도 언어 쿠키만 읽고 결과가 달라지지 않아야 한다.
- 판정 함수는 원본 헤더, 전체 Cookie 또는 사용자 식별값을 로그에 남기지 않아야 한다.

### 7.3 Proxy HTTP 계약 테스트

#### 경로와 메서드

| 요청                                                  | 기대 결과                                     |
| ----------------------------------------------------- | --------------------------------------------- |
| `GET /` + 한국어                                      | `307 /ko`                                     |
| `GET /` + 비한국어                                    | `307 /en`                                     |
| `HEAD /` + 한국어                                     | `307 /ko`, 응답 body 없음                     |
| `HEAD /` + 비한국어                                   | `307 /en`, 응답 body 없음                     |
| `POST /`, `PUT /`, `PATCH /`, `DELETE /`, `OPTIONS /` | 언어 Proxy 분기 없음, 기존 라우터의 상태 유지 |
| `GET /ko`, `/ko/`, `/ko/photo`                        | Proxy 개입 없음                               |
| `GET /en`, `/en/`, `/en/photo`                        | Proxy 개입 없음                               |
| `GET /admin`, `/api/*`, `/_next/*`                    | Proxy 개입 없음                               |
| `GET /favicon.ico`, `/robots.txt`, `/sitemap.xml`     | Proxy 개입 없음                               |
| `GET /photo`, `/albums`, `/about`                     | 기존 목적지로 308                             |
| `GET /enough`, `/korean`                              | 언어 세그먼트로 오인하지 않고 기존 404        |

GET과 HEAD만 처리한다는 계약은 구현에도 명시한다. 307이 메서드를 보존하므로 POST를 `/en`으로
보내면 의도하지 않은 POST 요청이 생길 수 있다.

#### Location과 URL 무결성

| 요청                            | 기대 결과                              |
| ------------------------------- | -------------------------------------- |
| `/?utm_source=test`             | `/ko` 또는 `/en`에 query 그대로 유지   |
| `/?a=1&a=2`                     | 중복 query와 순서 유지                 |
| `/?empty=&flag`                 | 빈 값과 값 없는 키 유지                |
| `/?q=%EC%84%9C%EC%9A%B8`        | percent encoding의 의미 유지           |
| Preview 도메인과 port 포함 요청 | 같은 origin의 언어 경로로 이동         |
| 조작된 Host·forwarded 헤더      | 외부 도메인으로 Location을 만들지 않음 |

목적지는 서버 내부 상수인 `/ko` 또는 `/en`만 사용한다. query의 값을 pathname이나 origin으로
사용하지 않아 open redirect가 불가능해야 한다. fragment는 서버에 전달되지 않으므로 자동화된
서버 테스트와 별개로 브라우저 테스트에서 확인한다.

#### 상태와 응답 헤더

- 상태는 모든 가변 결과에서 정확히 307이고 308, 301, 302가 아니다.
- `Location`은 선택 언어와 query를 포함한다.
- `Cache-Control`은 실제 응답에서 `private, no-store`다.
- 수동 선택이 아닌 `/` 판정 응답에는 `Set-Cookie`가 없다.
- 응답 body에 헤더, 쿠키 또는 내부 오류가 노출되지 않는다.
- 잘못된 입력에서도 5xx가 아니라 기본 `/ko` 또는 안전한 기존 응답을 반환한다.

### 7.4 언어 메뉴와 저장소 테스트

#### 정상 선택

- `/ko/photo?photo=1#details`에서 English 선택 시 `/en/photo?photo=1#details`로 이동한다.
- `/en/dev/projects?project=1`에서 한국어 선택 시 대응하는 `/ko/*`로 이동한다.
- 선택 직후 localStorage와 쿠키 값이 같은 언어다.
- 쿠키의 `Path`, `Max-Age`, `SameSite`, 운영 `Secure` 속성이 계약과 일치한다.
- 같은 언어를 다시 선택해도 값이 손상되거나 중복 쿠키가 생기지 않는다.
- 빠르게 `ko → en`을 선택하면 마지막으로 완료된 명시적 선택이 두 저장소와 URL에 일치한다.

#### 실패와 제한 환경

- localStorage 읽기 또는 쓰기가 throw해도 쿠키 기록과 현재 언어 이동은 가능한 범위에서 진행된다.
- `document.cookie` 쓰기가 차단돼도 localStorage 기록과 현재 언어 이동은 성공한다.
- 두 저장소가 모두 차단돼도 현재 페이지의 명시적 URL 이동은 성공한다.
- 오래된 legacy localStorage 값은 기존 마이그레이션 규칙을 유지한다.
- localStorage와 쿠키가 충돌하면 `/` 서버 판정은 쿠키를 사용하고, 명시적 다음 선택이 둘을 다시 맞춘다.
- 개발 HTTP 환경에서는 `Secure` 때문에 테스트 쿠키가 사라지지 않도록 환경별 속성을 검증한다.

#### 고지와 목적 제한

- 언어 선택 UI 또는 연결된 안내에서 언어가 30일간 저장된다는 내용을 접근할 수 있다.
- 수동 선택 전에는 언어 쿠키가 생성되지 않는다.
- 언어 쿠키를 GA 이벤트의 식별자나 사용자 속성으로 보내지 않는다.
- 쿠키 삭제 후 `/`는 다시 `Accept-Language` 정책을 따른다.

### 7.5 캐시·연속 요청 테스트

한 번의 응답만 검사하지 않고 같은 배포에 순서가 다른 요청을 연속으로 보낸다.

1. 영어 무쿠키 요청 `/ → /en`
2. 같은 URL의 한국어 무쿠키 요청 `/ → /ko`
3. 한국어 헤더 + `en` 쿠키 `/ → /en`
4. 영어 헤더 + `ko` 쿠키 `/ → /ko`
5. 다시 영어 무쿠키 요청 `/ → /en`

순서를 반대로도 실행해 앞선 사용자의 결과가 뒤 요청에 재사용되지 않는지 확인한다. Preview와
Production에서 CDN cache status 헤더를 기록하고, 일반 요청과 강제 cache bypass 요청의 결과가
같아야 한다. 서로 다른 query가 있어도 언어 판정 규칙은 같아야 한다.

### 7.6 렌더링·SEO 회귀 테스트

- 리다이렉트를 따른 `/ko` 문서의 `<html lang>`, title, description, canonical, OG locale이 한국어다.
- `/en` 문서의 같은 항목이 영어다.
- `/ko`와 `/en` 모두 자기 자신 canonical과 상호 hreflang을 가진다.
- sitemap에 두 언어 URL이 계속 포함되고 무언어 `/`만으로 대체되지 않는다.
- `x-default`는 결정한 기본 언어 `ko`와 일치한다.
- Googlebot과 유사한 헤더 없음 요청은 `/ko`로 가며, User-Agent를 바꿔도 결과가 달라지지 않는다.
- SNS/메신저 봇에는 `/ko` 또는 `/en` 직접 링크를 주었을 때 해당 언어 OG가 반환된다.
- 영어 필수 콘텐츠 누락 검사는 `/en` 공개 전에 실패 또는 경고한다.
- Privacy, Site Use & Content, Accessibility의 한국어·영어 페이지가 각각 200을 반환하고
  canonical·hreflang이 서로 연결된다.
- Footer와 분석 동의 UI의 Privacy 링크가 현재 언어 경로를 가리킨다.
- Privacy 본문의 쿠키 이름·보유 기간·GA 로딩 정책이 실제 상수 및 동작과 일치한다.

### 7.7 분석 동의와 독립성 테스트

확정된 GA4 동의 기능에 대해 다음을 검증한다.

- 분석 미동의 상태에서는 Google tag와 GA 네트워크 요청이 발생하지 않는다(Basic Consent Mode 기준).
- 분석 거부 후에도 언어 선택 쿠키와 `/` 라우팅은 정상 동작한다.
- 분석 허용은 언어 선택 쿠키를 만들거나 바꾸지 않는다.
- 언어 선택은 분석 동의를 허용한 것으로 처리되지 않는다.
- 저장값 없음·만료·손상 상태는 모두 미동의이며 현재 언어 배너를 표시한다.
- 허용 후 새로고침과 클라이언트 내비게이션에서 GA가 중복 초기화되거나 페이지뷰를 중복 전송하지 않는다.
- 거부 상태에서 새로고침·언어 전환·새 탭을 거쳐도 Google tag가 로드되지 않는다.
- 분석 동의를 철회하면 이후 페이지 이동에서 GA 이벤트가 중단된다.
- 철회 시 이 사이트가 만든 GA 쿠키 제거를 시도하고 실패해도 tag와 이벤트는 중단한다.
- 동의 UI의 허용과 거부는 한 화면에서 같은 클릭 수로 접근할 수 있고 키보드로 조작할 수 있다.
- Privacy 링크와 Footer의 설정 진입점으로 동의 선택을 다시 열 수 있다.
- 한국어·영어 URL에서 배너와 Privacy 링크의 언어가 각각 일치한다.

### 7.8 속성 기반·퍼즈 테스트

사례 표 밖의 입력을 보완하기 위해 언어 파서에 property-based 또는 fuzz 테스트를 적용할 수 있다.

- 임의의 문자열에서 함수가 throw하지 않는다.
- 어떤 입력에서도 반환값은 `ko | en | default` 중 하나다.
- 유효한 `ko` 최우선 항목 뒤에 더 낮은 `q` 항목을 추가해도 결과는 `ko`다.
- 유효한 비한국어 최우선 항목 뒤에 더 낮은 `q` 항목을 추가해도 결과는 `en`이다.
- 헤더 토큰의 대소문자만 바꿔도 결과는 같다.
- 의미 없는 허용 공백을 추가해도 결과는 같다.
- `q=0` 항목을 추가해도 기존 양수 최우선 결과는 바뀌지 않는다.
- 최대 입력 크기 내에서 실행 시간이 선형 범위를 벗어나지 않는다.

랜덤 테스트의 seed를 실패 메시지에 남겨 CI에서 재현할 수 있게 한다. 외부 파서 라이브러리를
사용한다면 우리 제품 정책을 감싸는 함수의 속성을 검증하고 라이브러리 내부 구현 자체를 복제해
테스트하지 않는다.

### 7.9 수동 운영 검증

- Chrome, Safari, Firefox의 최신 데스크톱·모바일에서 한국어, 영어, 일본어 설정을 확인한다.
- 시크릿 창과 일반 창을 비교해 기존 308 캐시 영향을 구분한다.
- 영어 브라우저에서 한국어 선택 후 `/`를 다시 열어 `/ko`로 가는지 확인한다.
- 한국어 브라우저에서 영어 선택 후 같은 절차로 `/en`을 확인한다.
- 쿠키 차단 환경에서 현재 언어 전환은 동작하고 재방문만 헤더 판정으로 돌아가는지 확인한다.
- 쿠키를 직접 삭제한 뒤 자동 판정으로 복귀하는지 확인한다.
- 브라우저 뒤로/앞으로, 새 탭, 새 창, 주소창 직접 입력에서 루프가 없는지 확인한다.
- SNS/메신저 미리보기 봇으로 `/ko`와 `/en` 직접 링크의 OG 메타데이터를 확인한다.
- Search Console URL 검사에서 `/ko`와 `/en`이 각각 접근 가능한지 확인한다.
- 실제 Vercel Production 응답의 status, Location, Cache-Control과 cache status를 보관한다.

## 8. 배포 순서

1. 영어 핵심 콘텐츠 누락을 점검한다.
2. 활성화된 운영 GA4를 Basic Consent Mode와 분석 동의 UI 뒤로 이동한다.
3. 쿠키/개인정보 안내에 언어 쿠키 계약을 추가한다.
4. 언어 판정 순수 함수와 테스트를 추가한다.
5. 언어 메뉴가 localStorage와 쿠키를 함께 갱신하게 한다.
6. `/` 전용 Proxy와 307·캐시 헤더를 추가한다.
7. `next.config.ts`에서 `/ → /ko` 308 하나만 제거한다.
8. 단위 테스트, 타입 검사, lint, production build 및 관련 E2E를 실행한다.
9. Preview 배포에서 헤더·쿠키·query 조합을 검사한다.
10. 프로덕션 배포 후 CDN 캐시를 정리하고 신규/시크릿 브라우저로 확인한다.
11. Search Console과 언어별 분석 지표를 관찰한다.
12. `CLAUDE.md`의 기존 “자동 분기 금지” 설명을 구현 정책에 맞게 개정하고 ADR-0002의
    “구현 대기” 표시를 제거한다.

문서 수정은 코드와 같은 변경 묶음에서 수행했다. 배포 환경에서만 확인할 수 있는 CDN·검색엔진
항목은 완료로 간주하지 않고 문서 상단과 아래 완료 조건에 남긴다.

## 9. 롤백 계획

문제가 발생하면 데이터 마이그레이션 없이 라우팅만 되돌릴 수 있다.

1. `/` 전용 Proxy matcher 또는 분기 로직을 제거한다.
2. `next.config.ts`에 `/ → /ko` 영구 리다이렉트를 복원한다.
3. CDN 캐시를 정리한다.
4. 언어 쿠키 쓰기는 남겨도 기존 화면 동작에 영향을 주지 않지만, 사용하지 않을 계획이면 별도
   호환 기간 후 제거한다.

롤백 판단 기준 예시:

- `/`에서 리다이렉트 루프 또는 5xx가 발생한다.
- 한국어·영어 사용자에게 동일한 캐시된 목적지가 광범위하게 제공된다.
- `/ko` 또는 `/en` 직접 접근이 자동으로 반대 언어로 바뀐다.
- Search Console에서 언어 URL 접근이나 hreflang 오류가 유의미하게 증가한다.
- 영어 랜딩의 즉시 언어 재전환율 또는 이탈률이 예상보다 크게 악화된다.

## 10. 운영 트러블슈팅 런북

### 증상 A: 영어 브라우저가 계속 `/ko`로 간다

확인 순서:

1. 요청 URL이 `/`인지, 과거 URL(`/photo` 등)인지 확인한다. 과거 URL은 의도적으로 `/ko/*`다.
2. 언어 선택 쿠키가 `ko`로 저장되어 있는지 확인한다.
3. 실제 요청의 `Accept-Language` 최우선 값이 무엇인지 확인한다.
4. 브라우저가 과거 `/ → /ko` 308을 캐시했는지 시크릿 창과 다른 URL에서 비교한다.
5. `next.config.ts`의 기존 루트 308이 남아 Proxy보다 먼저 실행되는지 확인한다.
6. Preview와 Production의 배포 버전이 같은지 확인한다.

조치:

- 잘못된 `ko` 쿠키면 언어 메뉴에서 영어를 다시 선택하거나 쿠키를 지운다.
- 기존 308 캐시면 `/en` 직접 링크를 제공하고 캐시가 자연 해소되도록 한다.
- 서버 규칙 문제면 `/` 308 제거와 Proxy matcher를 수정한 뒤 재배포한다.

### 증상 B: 한국어 브라우저가 `/en`으로 간다

확인 순서:

1. `en` 선택 쿠키가 있는지 확인한다.
2. 브라우저 설정에서 실제 최우선 언어가 한국어인지 확인한다.
3. `Accept-Language`의 `q` 우선순위가 예상과 같은지 확인한다.
4. CDN에서 다른 사용자의 응답을 공유했는지 응답 캐시 헤더를 확인한다.

조치:

- 명시적 `en` 쿠키는 정상 동작이므로 사용자가 한국어를 선택하면 갱신한다.
- 캐시 공유라면 `/` 응답을 `private, no-store`로 교정하고 CDN 캐시를 제거한다.

### 증상 C: 사용자가 언어를 선택해도 다음 방문에 유지되지 않는다

확인 순서:

1. localStorage `ap-lang:v1`과 언어 쿠키가 모두 갱신됐는지 확인한다.
2. 쿠키의 `Path=/`, 만료, `Secure`, 도메인 속성을 확인한다.
3. 브라우저 또는 확장 프로그램이 쿠키를 차단하는지 확인한다.
4. 언어 메뉴 내비게이션 전에 쿠키 쓰기 코드가 실행되는지 확인한다.

조치:

- 쿠키 속성을 현재 운영 도메인에 맞춘다.
- 쿠키 실패는 UI 전환 실패로 이어지지 않게 유지한다.
- 쿠키 차단 환경은 `Accept-Language` 폴백이 정상 동작하는지 확인한다.

### 증상 D: 모든 사용자가 같은 언어로 간다

확인 순서:

1. `/` 응답의 `Cache-Control`이 실제로 `private, no-store`인지 확인한다.
2. Vercel/CDN 응답의 cache status 헤더를 확인한다.
3. Preview와 Production에서 한국어·영어 요청을 연속으로 보내 결과가 섞이는지 비교한다.
4. 언어 파서가 항상 기본값을 반환하는지 단위 테스트한다.

조치:

- 공유 캐시를 비활성화하고 CDN 캐시를 제거한다.
- Proxy에서 응답마다 요청 헤더를 읽는지 확인한다.

### 증상 E: `/ko`와 `/en` 사이에서 루프가 발생한다

확인 순서:

1. Proxy matcher가 `/`보다 넓게 설정됐는지 확인한다.
2. 이미 로컬라이즈된 경로를 감지하기 전에 리다이렉트하는지 확인한다.
3. Vercel 설정이나 다른 redirect 규칙이 언어 경로를 다시 `/`로 보내는지 확인한다.
4. 클라이언트 언어 초기화 코드가 URL과 다른 언어로 `router.push`하는지 확인한다.

조치:

- Proxy를 `/`에만 적용한다.
- URL 언어를 쿠키와 브라우저 언어보다 우선한다.
- 상충하는 리다이렉트 규칙을 제거한다.

### 증상 F: `/en` 페이지에 한국어 문장이 섞인다

확인 순서:

1. 해당 Firestore 또는 mock 데이터의 `en` 필드가 비어 있는지 확인한다.
2. `pickText` 폴백으로 한국어가 선택됐는지 확인한다.
3. navigation 사전과 페이지 메타데이터도 함께 확인한다.

조치:

- 누락된 영어 콘텐츠를 입력한다.
- 콘텐츠 검증 결과에 번역 누락 상태를 노출한다.
- 빈 영어 값을 숨길지 한국어로 폴백할지는 콘텐츠 유형별 정책에 따른다.

### 증상 G: UTM 파라미터나 캠페인 분석이 사라진다

확인 순서:

1. `Location` 응답 헤더에 원래 query가 포함되는지 확인한다.
2. Proxy가 pathname만 새 URL로 만들고 search params를 버리는지 확인한다.
3. 최종 `/ko` 또는 `/en` 페이지에서 GA가 query 포함 경로를 정상 수집하는지 확인한다.

조치:

- 원래 `request.nextUrl`을 복제하고 pathname만 변경하는 방식으로 교정한다.
- query 보존 E2E를 회귀 테스트로 유지한다.

## 11. 관찰 지표

최소 2주 동안 다음 지표를 배포 전 같은 기간과 비교한다.

| 지표                        | 해석                                                |
| --------------------------- | --------------------------------------------------- |
| `/ko`, `/en` 랜딩 세션 비율 | 해외 유입이 실제 영어 랜딩으로 이동했는지 확인한다. |
| 언어별 이탈률·체류 시간     | 영어 페이지가 해외 방문자에게 유용한지 본다.        |
| 진입 직후 언어 메뉴 전환율  | 자동 판정의 오탐 또는 콘텐츠 품질 문제를 찾는다.    |
| `/` 리다이렉트 오류율       | Proxy 예외와 잘못된 Location을 감시한다.            |
| `/ko`, `/en` 검색 노출      | 검색 색인과 hreflang 상태가 안정적인지 확인한다.    |
| 영어 콘텐츠 누락 수         | 자동 영어 유입 전후의 번역 품질을 관리한다.         |

트래픽이 적으면 퍼센트만 보고 결론 내리지 않고 실제 세션 수를 함께 본다. 기존 308을 기억하는
재방문자 때문에 배포 직후 `/ko` 비율이 예상보다 높을 수 있다.

안내한다. 이 계획은 그 위험을 줄이기 위해 언어가 없는 진입점에서만 목적지를 추천하고, 명시적

사용자 선택보다 우선하지 않는다.
